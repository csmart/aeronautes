Aeronautes 0.5.0 is the first tagged release: a desktop workbench for OpenStack Swift and SwiftStack that browses, inspects, edits, transfers and deletes with the store's own semantics made explicit.

**Read before using it against data that matters.**
These builds are unsigned, and only Linux is supported, on x86_64 and aarch64: Fedora current stable is the reference platform, and the deb targets Ubuntu current LTS, where the package installs, verifies and removes cleanly in a fresh container but the window has not yet had its own acceptance run.
The valuable-data release hold remains: the evidence its acceptance gates require is not complete, so use dedicated test accounts and containers first, as the [README](https://github.com/csmart/aeronautes#before-trusting-a-release-against-production) describes.

## What it does

- Browse containers and very large containers page by page, with Logical, All and Backstage views, Find, and prefix counts; the "/" folder some stores leave out of a container's top is shown too.
- Containers that are only named like segment stores sit under a "Possible backstage" heading that starts closed, and a container that is or may be a segment store says so above its listing and in its delete dialogs.
- The container list is read again from its own refresh button, and when you come back to the window after half a minute away, so a change made with another tool shows without reconnecting.
- Act on a row or a container from its right-click menu, which offers the toolbar's own actions for it.
- Inspect accounts, containers and objects: headers, metadata, ACLs, storage policies, large objects (DLO and SLO) and their segments.
- Edit object, container and account metadata, container ACLs (with a native confirmation before anything is made public), quotas, TempURL keys, CORS and legacy versioning locations; create containers with a storage policy.
- Upload files or a whole folder, and download or copy what is selected (chosen objects, one object, a folder or a container), copying between bookmarks too, each checked completely before anything is written; replacing an existing object needs a native confirmation.
- Choose a copy's destination container from that account's list, or create it when the preview finds it missing.
  A copied folder keeps its name: the destination folder path starts as the folder's name, and clearing it copies the folder's contents alone.
- Upload large files in segments as static large objects, or as dynamic ones where the store cannot read static ones back, where the container keeps versions, or where the bookmark asks for them.
- Delete an object, a selection, a marker, a manifest, a prefix or a container's contents, with a preview of what will go. A single object, marker or manifest is confirmed with a button; a selection asks you to type its count, a prefix deletion the container and the prefix, emptying a container `empty` and its name, and deleting a container `delete` and its name. Emptying and deleting a container are separate actions, each with its own dialog. A large object's segments go with it unless you untick the option that says so: for one object its delete dialog's "Also delete the segments", with the object's name typed, and for every large object of a prefix or container deletion "Also delete the segments of large objects", with the scope typed followed by `and segments`. Each name is deleted by one request, and the store's answer to it is the result.
- Run up to four jobs at once (two by default), pause and resume them, and read each job's per-object records and recorded settings.
- Authenticate with TempAuth v1 or Keystone v3, which finds its v3 endpoint from an Identity URL at the same address and takes user and project IDs as well as names; credentials stay in the system keyring.
- Import bookmarks from an rclone.conf or a clouds.yaml with its secure.yaml, from Settings, the rail or the welcome dialog, naming each in the preview; each is verified in the background and flagged if it does not sign in, and its key goes to the system keyring.
- Duplicate a bookmark for another account on the same cluster; the copy asks for its own key. A bookmark with no saved key is marked on the rail and opens its editor for the key when chosen.
- Keep the application's settings in one Settings view, including backup and restore of the configuration, without credentials.

## In this build beyond 0.5.0's plan

Uploads and downloads take the performance profile and per-job overrides the copy dialog already offered, and each job records where each value came from.

## Where your files are

- Settings: `~/.config/aeronautes/settings.json`, a JSON file you can read and edit.
- Bookmarks, jobs, recovery records and the audit trail: `~/.local/share/aeronautes/aeronautes.sqlite`, with custom CA certificates in `ca/` beside it.
- Keys and passwords: the system keyring, never either file.

Development builds before this release kept everything in `~/.local/state/aeronautes/state.sqlite`, which 0.5.0 does not read; the [README](https://github.com/csmart/aeronautes#where-aeronautes-keeps-its-files) says how to move it, with its `-wal` and `-shm` files, and that its settings return to their defaults.

## Files

For each architecture: an rpm, a deb and a tarball, each carrying the pinned rclone v1.74.3 it verifies before use, and a `.provenance.json` with every file's SHA256.
macOS and Windows builds are development builds without acceptance and are not attached.

## Installing

The packages are unsigned, so give the package manager the file itself.

- Fedora: `sudo dnf install ./<the rpm>`. It needs `gtk4` and `webkitgtk6.0`, which dnf installs with it.
- Ubuntu 24.04: `sudo apt install ./<the deb>`. It needs `libgtk-4-1` and `libwebkitgtk-6.0-4`, which apt installs with it.
- Tarball: unpack it anywhere and run `./aeronautes`, keeping `rclone` beside it. It needs the same GTK 4 and WebKitGTK 6 libraries from your distribution.

A package puts the program in `/usr/local/bin` with an entry for it in the application menu, and its rclone in `/usr/local/libexec/aeronautes`.
`aeronautes --version` then reports the version and the source revision, and `aeronautes --engine` the bundled rclone and that it verified.
Remove it with `sudo dnf remove aeronautes` or `sudo apt remove aeronautes`; that leaves your settings, bookmarks and keys where they are.

## Known issues

- No whole-application memory ceiling: a download's plan holds its whole inventory, measured on the development host at about 352 MiB of peak resident memory at the default limit of 250,000 objects, and many large downloads queued together can hold several GiB.
- Mirror is not offered: it refuses every start until it can protect concurrent changes, so the copy dialog has no Mirror tab.
- Deleting a large object, alone or with its folder or container, deletes its segments too, because the option that does so starts ticked; untick it to keep them.
  Nothing can show that another object does not use the same segment, and one that does loses its data; the dialogs say so, and the words you type name the segments.
  A selection of objects has no such option yet, so a selected large object keeps its segments, which still count against quota.
  A container that keeps versions keeps every segment: the store keeps a deleted large object in the archive container as a version that still uses them.
  Deleting that container moves what it held into its archive and leaves the archive; delete the archive container, as a second deletion, to remove the versions and their segments.
  In a container that is another container's archive the option starts unticked, because an archived version and the current object can use the same segments.
  Where a large object's segments cannot be bounded safely the option keeps them and the job ends partial, saying why.
  Segments left by an earlier deletion have no manifest to name them: this application and rclone usually keep them in a container named after the first with `_segments` added, which the delete dialog names and, once the deletion is done, offers to open, and whether anything still uses what is there is for you to judge.
- A selection's folders are not copied or downloaded yet: with files and folders selected together only the files are taken, and several folders selected alone cannot be taken in one go.
  The window says so in a warning before either dialog opens, naming the folders left out.
  To take a folder with everything in it, select that folder alone; to take everything, press Escape to clear the selection and copy or download the folder or container you are in.
- Nothing here guards against another program writing to the same names at the same time: the store decides, and the last request to a name wins.
  A deletion deletes whatever a name holds when its request arrives, so an object another program wrote after you looked goes with the rest; the delete dialogs say so.
  Nothing is read again afterwards to check a deletion: an object the store accepted the request for is reported deleted, and one it gave no answer for is reported unknown.
  An upload writes each file straight to its name, over whatever is there when its request arrives: a name the preview found free, and so did not ask you about, is replaced without a question if another program created it in between.
- A copy writes each object straight to its name as well, and reads nothing back afterwards: an object the transfer engine reports written is reported copied.
  It skips a name the two listings show with the same size and tag without reading either object, so an object whose metadata alone changed at the source is not copied again.
  Two static large objects whose listings show the same size and segment hash are skipped from the listings as well.
  Any other large object, and an empty one, cannot be compared from the listings, so each side is read once: it is skipped only when the store reports the same size and tag for both, which holds when both were written at the same chunk size, and otherwise counts as different.
  A name that counts as different is replaced if you confirmed replacing, and refused, with the job ending partial, if you did not.
- A copied object keeps its source's content type, metadata, content encoding and disposition, and expiry; the transfer engine also records the source's modification time on it in the metadata key `Mtime`.
  The metadata is set in a second request after the object is written, so a copy that fails between the two leaves the object at its name without it and says so in that object's record.
- An upload or a copy that replaces a large object removes that object's old segments only where the transfer engine may delete: under the folder being written to, in the destination's `_segments` container.
  Old segments kept anywhere else stay and still count against quota, as do those of an object whose name the application sends itself.
  Nothing is removed where the container keeps versions, or where "Reclaim replaced segments" is off in Settings; the question you answer before a replacement says which applies.
- An uploaded object carries its file's modification time in the metadata key `Mtime`, as the transfer engine writes it; editing the object's metadata keeps the key unless you remove it.
- Where the container keeps versions, a large file uploads as a dynamic large object whatever the bookmark or the job asks for, and the upload dialog says so: a static one would leave an extra version of each file in the archive.
- A large upload that fails or is cancelled can leave segments with no object to name them; the job's record names where the engine put them, and nothing removes them for you.
