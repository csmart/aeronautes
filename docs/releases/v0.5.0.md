Aeronautes 0.5.0 is the first tagged release: a desktop workbench for the OpenStack Swift API and compatible implementations that browses, inspects, edits, transfers and deletes with the store's own semantics made explicit.

**Read before using it against data that matters.**
These builds are unsigned, and only Linux is supported, on x86_64 and aarch64: Fedora current stable is the reference platform, and the deb targets Ubuntu current LTS, where the package installs, verifies and removes cleanly in a fresh container but the window has not yet had its own acceptance run.
The valuable-data release hold remains: the evidence its acceptance gates require is not complete, so use dedicated test accounts and containers first, as the [README](https://github.com/csmart/aeronautes#before-trusting-a-release-against-production) describes.

## What it does

- Browse containers and very large containers page by page, with Logical, All and Backstage views, Find, and prefix counts; the "/" folder some stores leave out of a container's top is shown too.
  When a folder's listing reaches the retention ceiling set in Settings, "Next" shows the following rows in place of those shown, and "Back to the start" returns to the first row; a page change clears the selection.
- Containers that are only named like segment stores sit under a "Possible backstage" heading that starts closed, and a container that is or may be a segment store says so with a mark beside its path and in its delete dialogs.
- The container list is read again from its own refresh button, and when you come back to the window after half a minute away, so a change made with another tool shows without reconnecting.
- The listing stays where it is: a public container, a segment store, a backstage listing or a count is a short mark or text on the path's row, with the whole sentence on hover, never a line that pushes the list down. Refresh and "#" (count) are at the right end of that row; "#" counts the one folder selected, or else where you are.
- Act on a row or a container from its right-click menu, which offers the toolbar's own actions for it. With rows selected the deletions' row offers only their deletion, never the folder's or the container's; a press in the list's empty space clears the selection.
- Find a container by any part of its name with the filter above the Containers list, and create a folder by name with "New folder…".
- The inspector's actions sit under each item's name; every value in its cards has a copy button; a metadata key field suggests keys, found by any part of the name, with what each does: the static website and cross-origin keys for a container, `Mtime` for an object, and keys used elsewhere this session.
- A container's counts are read again a few seconds and half a minute after a job that changed it, since the store updates them in the background.
- "Use the graphics card" in Settings turns the window's hardware acceleration off for a system whose graphics driver makes it slow or blank; it applies at the next start.
- Inspect accounts, containers and objects: headers, metadata, ACLs, storage policies, large objects (DLO and SLO) and their segments.
- Edit object, container and account metadata, container ACLs (with a native confirmation before anything is made public), quotas, TempURL keys, CORS and legacy versioning locations; create containers with a storage policy.
  Where the store's `/info` does not list TempURL, static websites or container quotas, their editors are greyed with a sentence saying so, since the store would keep the setting and not act on it.
- Upload files or a whole folder, and download or copy what is selected (chosen objects and folders, one object, a folder or a container), copying between bookmarks too, each checked completely before anything is written; replacing an existing object needs a native confirmation.
- Choose a copy's destination container from that account's list, or create it when the preview finds it missing.
  A copied folder keeps its name: the destination folder path starts as the folder's name, and clearing it copies the folder's contents alone.
  A downloaded folder keeps its name as well: "Download folder…" writes it as a folder of its own name inside the directory you choose, while "Download container…" writes the container's contents straight into it.
- A selected folder is copied or downloaded with everything in it, beside the selected objects, however many folders are selected, and keeps its name at the destination, as rclone does when it copies a folder; a selected folder with nothing in it is reported as no longer at the source.
  Within one container a copy is refused, before anything is written, when it would write into a selected folder or over something it is still reading; the message names where.
  A deletion's selection takes a selected folder the same way, with everything in it, and its large objects lose their segments as a folder deletion's do unless you untick the option.
- Upload large files in segments as static large objects, or as dynamic ones where the store cannot read static ones back, where the container keeps versions, or where the bookmark asks for them.
- Delete an object, a selection, a marker, a manifest, a prefix or a container's contents, with a preview of what will go. Every deletion is confirmed by typing `delete` and what it deletes: an object or a marker its name, a selection its count, a prefix the container and the prefix, and a container its name; emptying a container is typed as `empty` and its name, and a manifest deleted on its own is confirmed with a button. Emptying and deleting a container are separate actions, each with its own dialog. A large object's segments go with it unless you untick the option that says so: for one object its delete dialog's "Also delete the segments", with the object's name typed, and for every large object of a prefix or container deletion "Also delete the segments of large objects", with the scope typed followed by `and segments`. Each name is deleted by one request, and the store's answer to it is the result.
- Run up to four jobs at once (two by default), pause and resume them, and read each job's per-object records and recorded settings.
  An upload or a download shows each file in the jobs drawer as soon as the transfer engine reports it written or already the same, rather than when a whole folder or batch is done.
  Settings shows the running and waiting limits together with how many jobs that admits at most, and a start beyond it is refused naming both counts.
- Authenticate with TempAuth v1 or Keystone v3, which finds its v3 endpoint from an Identity URL at the same address and takes user and project IDs as well as names; credentials stay in the system keyring. A sign-in the store does not answer, such as one met by a TLS alert, is tried up to three more times, two seconds apart, before it fails.
- Import bookmarks from an rclone.conf or a clouds.yaml with its secure.yaml, from Settings, the rail or the welcome dialog, naming each in the preview; each is verified in the background and flagged if it does not sign in, and its key goes to the system keyring.
- Duplicate a bookmark for another account on the same cluster; the copy asks for its own key. A bookmark with no saved key is marked on the rail and opens its editor for the key when chosen.
- Keep the application's settings in one Settings view, including backup and restore of the configuration, without credentials; filter it by any part of a setting's name or note, and reset every setting to this version's defaults after a question.
- A transfer's preview names each problem in words, such as "Overlaps a running download" or "Already exists", with its whole reason.
- A download's job names the folder you picked, and an upload's the folder its files came from, in the jobs drawer, Copy details and the history.
- Settings has a Diagnostics section: the log level (debug, info, warn or error) applies at once, and "Keep a log file" writes the log to `~/.local/state/aeronautes/aeronautes.log`, shown with a copy button, starting again past 10 MiB. The `AERONAUTES_LOG_LEVEL` and `AERONAUTES_LOG_FILE` switches still work and win at launch.

## In this build beyond 0.5.0's plan

Uploads and downloads take the performance profile and per-job overrides the copy dialog already offered, and each job records where each value came from.

## Where your files are

- Settings: `~/.config/aeronautes/settings.json`, a JSON file you can read and edit.
- Bookmarks, jobs, recovery records and the audit trail: `~/.local/share/aeronautes/aeronautes.sqlite`, with custom CA certificates in `ca/` beside it.
- Keys and passwords: the system keyring, never either file.
- The log file, only while "Keep a log file" is on in Settings: `~/.local/state/aeronautes/aeronautes.log`, and the one before it as `aeronautes.log.1`.

Development builds before this release kept everything in `~/.local/state/aeronautes/state.sqlite`, which 0.5.0 does not read; the [README](https://github.com/csmart/aeronautes#where-aeronautes-keeps-its-files) says how to move it, with its `-wal` and `-shm` files, and that its settings return to their defaults.

## Files

For Linux on each architecture: an rpm, a deb and a tarball, each carrying the pinned rclone v1.74.3 it verifies before use, and a `.provenance.json` with every file's SHA256.
Unsigned Windows portable ZIPs and macOS app-bundle ZIPs are also attached for x86_64 and aarch64, with their own provenance records and pinned engine.
These additional bundles are provided for testing; their native desktop acceptance remains incomplete.
They are not Windows MSI/EXE installers or macOS DMG/PKG installers.

## Installing

The packages are unsigned, so give the package manager the file itself.

- Fedora: `sudo dnf install ./<the rpm>`. It needs `gtk4` and `webkitgtk6.0`, which dnf installs with it.
- Ubuntu 24.04: `sudo apt install ./<the deb>`. It needs `libgtk-4-1` and `libwebkitgtk-6.0-4`, which apt installs with it.
- Tarball: unpack it anywhere and run `./aeronautes`, keeping `rclone` beside it. It needs the same GTK 4 and WebKitGTK 6 libraries from your distribution.
- Windows: extract the whole ZIP and run `aeronautes.exe`, keeping `rclone.exe` beside it.
- macOS: extract the ZIP and move `aeronautes.app` to Applications.

Windows SmartScreen and macOS Gatekeeper may warn or block launch because the builds are unsigned and macOS builds are not notarised.

A package puts the program in `/usr/local/bin` with an entry for it in the application menu, and its rclone in `/usr/local/libexec/aeronautes`.
`aeronautes --version` then reports the version and the source revision, and `aeronautes --engine` the bundled rclone and that it verified.
Remove it with `sudo dnf remove aeronautes` or `sudo apt remove aeronautes`; that leaves your settings, bookmarks and keys where they are.

## Known issues

- No whole-application memory ceiling: a download's plan holds its whole inventory, measured on the development host at about 352 MiB of peak resident memory at the default limit of 250,000 objects, and many large downloads queued together can hold several GiB.
- Mirror is not offered: it refuses every start until it can protect concurrent changes, so the copy dialog has no Mirror tab.
- Deleting a large object, alone or with its folder or container, deletes its segments too, because the option that does so starts ticked; untick it to keep them.
  Nothing can show that another object does not use the same segment, and one that does loses its data; the dialogs say so, and the words you type name the segments.
  A selection of objects has no such option yet, so a selected large object keeps its segments, which still count against quota.
  A container that keeps versions keeps every segment: the store keeps a deleted large object in the archive container as a version that still uses them.
  Deleting that container moves what it held into its archive and leaves the archive; delete the archive container, as a second deletion, to remove the versions and their segments.
  In a container that is another container's archive the option starts unticked, because an archived version and the current object can use the same segments.
  Where a large object's segments cannot be bounded safely the option keeps them and the job ends partial, saying why.
  Segments left by an earlier deletion have no manifest to name them: this application and rclone usually keep them in a container named after the first with `_segments` added, which the delete dialog names and, once the deletion is done, offers to open, and whether anything still uses what is there is for you to judge.
- Nothing here guards against another program writing to the same names at the same time: the store decides, and the last request to a name wins.
  A deletion deletes whatever a name holds when its request arrives, so an object another program wrote after you looked goes with the rest; the delete dialogs say so.
  Nothing is read again afterwards to check a deletion: an object the store accepted the request for is reported deleted, and one it gave no answer for is reported unknown.
  An upload writes each file straight to its name, over whatever is there when its request arrives: a name the preview found free, and so did not ask you about, is replaced without a question if another program created it in between.
- A copy writes each object straight to its name as well, and reads nothing back afterwards: an object the transfer engine reports written is reported copied.
  It skips a name the two listings show with the same size and tag without reading either object, so an object whose metadata alone changed at the source is not copied again.
  Two static large objects whose listings show the same size and segment hash are skipped from the listings as well.
  Any other large object, and an empty one, cannot be compared from the listings, so each side is read once: it is skipped only when the store reports the same size and tag for both, which holds when both were written at the same chunk size, and otherwise counts as different.
  A name that counts as different is replaced if you confirmed replacing, and refused, with the job ending partial, if you did not.
- A copied object keeps its source's content type, metadata, content encoding and disposition, and expiry; the transfer engine also records the source's modification time on it in the metadata key `Mtime`.
  The metadata is set in a second request after the object is written, so a copy that fails between the two leaves the object at its name without it and says so in that object's record.
- A download writes each file straight into the folder you chose, and reads nothing back afterwards: a file the transfer engine reports written is reported downloaded.
  Unless you ask it to replace, it never replaces a file of yours: the preview refuses a name that is already in the folder, and a file that appears there after the preview is left alone and reported as not downloaded, with the job ending partial.
  The engine looks at a name once, just before it writes it, so a file you create in that moment is replaced.
- An upload or a download whose preview finds names already in use offers to replace them, as a copy does, and the application asks once, on its own dialog, before anything is written; a download's question names the folder and says that a replaced file is not kept.
  Confirmed, the transfer engine compares each name as rclone copy does and replaces only what differs: a name of another size is replaced; one of the same size and modification time is left as it is; one of the same size with only another time keeps its bytes and takes the source's time when its MD5 matches, and is replaced when it does not.
  A large object has no MD5 at the store, so one whose time alone differs is sent again in full.
  A file whose bytes changed but whose size and time did not is not replaced, as with rclone copy used alone.
  When any file of an upload is large enough to go in segments, the engine is told to ignore sizes for that whole upload: a file whose time matches is left as it is even when its size changed, and one whose time differs is still kept when its MD5 matches and replaced when it does not.
  The jobs drawer counts the names left because they were already the same, and each transfer's per-job settings say how it decides; nothing changes the rule yet.
  A download whose transfer engine was stopped hard can leave a file it was writing in the folder under a name ending `.partial`; the job says so, and a folder upload of that folder takes that file too.
  If another program replaces a folder inside the chosen folder with a link while a download writes into it, the transfer engine follows the link, as rclone does, and the files are written where the link points.
- An upload or a copy that replaces a large object removes that object's old segments only where the transfer engine may delete: under the folder being written to, in the destination's `_segments` container.
  Old segments kept anywhere else stay and still count against quota, as do those of an object whose name the application sends itself.
  Nothing is removed where the container keeps versions, or where "Reclaim replaced segments" is off in Settings; the question you answer before a replacement says which applies.
- An uploaded object carries its file's modification time in the metadata key `Mtime`, as the transfer engine writes it; editing the object's metadata keeps the key unless you remove it.
- Where the container keeps versions, a large file uploads as a dynamic large object whatever the bookmark or the job asks for, and the upload dialog says so: a static one would leave an extra version of each file in the archive.
- A large upload that fails or is cancelled can leave segments with no object to name them; the job's record names where the engine put them, and nothing removes them for you.
