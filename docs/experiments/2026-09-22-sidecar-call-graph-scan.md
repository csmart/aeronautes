# Sidecar advisory call-graph scan — 22 September 2026

The oracle is P31 and SEC-11 in the [remediation plan](../audits/2026-09-05/remediation-plan.md#acceptance-gates-and-completion): every retained advisory needs an enabled-path disposition and every shipped sidecar a scan, narrowed by the operator's 22 September decisions in the [finish line](../audits/2026-09-05/linux-finish-line.md) (decision 1 makes the two Linux packages the claimed targets; decision 5 resumed this work).
The [12 September record](2026-09-12-advisory-dispositions.md) carried 42 rows at module precision, because binary-mode scanning of the stripped sidecars fell back to module precision, and its unknown rows asked for the callers and inputs of the affected symbols.
This record supplies the static call graph of the sidecar's own build and a direct call-site inventory of the same build, and re-proposes the thirty rows they reach.
No row is accepted here, no advisory trigger was executed and no candidate engine was run.

## Method

The evidence is retained privately in `.aeronautes-work/20260922-p31-govulncheck/` with `SHA256SUMS` and `HOST.md`.

- Source: rclone at `37e4117f48bdef0fa1ba27f6467d7a891b0b55ba`, extracted from the retained archive whose SHA256 (`01312af4…26c7`) matches the 9 September provenance record; the same revision the pinned sidecar embeds.
- Selected build: the settings the pinned Linux amd64 sidecar reports through `go version -m`: go1.26.4, `v1.74.3+dirty`, `-tags=cmount`, `CGO_ENABLED=0`, `GOOS=linux`, `GOARCH=amd64`, `vcs.modified=true`; the scan targets the main package only, so the graph is the binary's, not the test suite's.
  The accepted arm64 sidecar's own settings were not re-read here; the retained v1.75.1 arm64 candidate reports the same tag and `CGO_ENABLED=0`, and the arm64 scan assumes the accepted arm64 binary was built the same way (a listed gap).
- Scanner: govulncheck v1.8.0 against the vulnerability database of 16 September 2026, in source mode, for linux/amd64 and linux/arm64, under two toolchains.
  Under Go 1.27.1 the standard-library advisories are judged against 1.27.1 and disappear (21 advisories); under `GOTOOLCHAIN=go1.26.4`, the sidecar's release, 30 advisories are reported, and that run is the one the rows use.
  The text reports are byte-identical across the two architectures and every advisory has the same result in both JSON streams.
- Call-site inventory: `go list -deps` of the same selection lists 1,614 packages (1,611 on arm64); a textual search of every non-test Go file in those packages, under all build tags, for the advisories' vulnerable functions (`call-sites-linux-amd64.txt`).
  It over-approximates (it counts names in files the build may exclude) and it is complete for direct calls; a call through `reflect.Value.Call` would appear in neither the graph nor the inventory.
- Reading the graph: govulncheck reports one representative chain per vulnerable symbol from `main` or an `init` of the binary over a static graph (variable type analysis) that over-approximates through function values and interfaces.
  So "called" is an upper bound with a representative route, not an exhaustive list of routes; "imported" (the package is in the build but no vulnerable symbol is reachable) and "module" (no affected package is in the build) are complete negative results for that graph.
  Go's `plugin` package is a stub without cgo (`plugin: not implemented` in `plugin_stubs.go`), so `lib/plugin` cannot load code into this build.

## What this closes and what it does not

The graph and the inventory answer the caller questions the 12 September record left open: the image decoders have one consumer (the Internxt upload thumbnail path), `os.Root`, chi's `RealIP`, `s2.NewDict`, the baggage parser, the gRPC server and `LookupCNAME` are reachable from nothing, no `golang.org/x/crypto/openpgp` package is in the build, ASN.1 and XML decoding belong to unselected options and backends, and the only URL-reference callers are the client's redirect path, which the gateway cuts, and unselected backends.
Normalisation stays on the enabled route and rests on the application's UTF-8 admission.

What remains:

- Source-to-binary correspondence: both Linux sidecars report `vcs.modified=true`; this scan is of the public revision, and no reproducible build is claimed.
- The accepted arm64 sidecar's build settings were not re-read.
- "Called" rows rest on representative chains plus the direct-call inventory, not on an exhaustive path enumeration; a reviewer who wants exhaustive paths needs a full call-graph dump, which govulncheck does not emit.
- The twelve rclone-module advisories, the application, native-library and npm scopes, and the compatibility gate for any engine update are untouched.
- Acceptance is the reviewer's and the operator's; SEC-11, P31 and the valuable-data hold stay open.
