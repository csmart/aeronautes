# 0.5.0 test plan

Written on 11 November 2026 for the operator's decision of the same day to cut 0.5.0 as the first tagged release, with its Linux packages published on GitHub, after the operator has run this plan against the release candidate.
It supersedes the [0.1.0 test plan](../2026-09-24/0.1.0-test-plan.md), which was never run: its steps 1 to 7 are carried here with the changes stated, steps 8 to 18 cover what 0.2.0 to 0.5.0 added and the fixes from the first test run, and step 19 covers what was added for the final candidate.
Every step is run by the operator on a Linux workstation; none of it can be driven headless, which is why these checks are here rather than in CI.
A failed step blocks the tag ([RELEASING](../../RELEASING.md)).
Results go in `0.5.0-test-results.md` beside this plan, one row per step: what was observed, pass or fail, and where the evidence is (log path or screenshot).
Where an expected sentence below is quoted, record the exact text if the application's differs; a different wording is a note, a different meaning is a finding.

## Before starting

- The candidate is the Linux packages a release-workflow dispatch builds from the commit to be tagged; the author downloads them into the evidence packet and names the directory. They report the version `dev` with the commit's full revision; the tag build of the same commit stamps `v0.5.0`.
- The 0.1.0 plan's "Before starting" applies, with one change: the active-job budget now defaults to two and allows four.
- Steps 8 and 14 delete and pause real objects and jobs, and steps 19b, 19g, 19i, 19j, 19k, 19n, 19o, 19p, 19q and 19s copy objects, create and delete containers and upload objects: run them against SAIO or containers and accounts made for the test, never against data that matters.
- Step 11c needs a Keystone v3 endpoint; if none is available, record it as not run, which does not block the tag.
  Step 19d needs the same endpoint.
- Steps 19e and 19m write test accounts' keys into an rclone.conf: use accounts made for the test, and delete the file afterwards.
- Run the application from a terminal so its output is retained, and keep the jobs drawer's "Recent changes" tab in view when a step says so.

## Steps 1 to 7, carried from the 0.1.0 plan

Run steps 1 to 7 of the [0.1.0 plan](../2026-09-24/0.1.0-test-plan.md) as written, with these changes.

- Step 1: the rpm under test is the 0.5.0 candidate's. If an Ubuntu 24.04 host is available, also install the candidate deb there (`sudo apt install ./<name>.deb`), run `aeronautes --engine` and `aeronautes --version`, and remove it; record it as not run otherwise.
- Step 4: the settings it names are in the Settings view, opened from the gear at the foot of the bookmark rail, not in the jobs drawer; the notes and statuses beside each are worded as the view shows them.
- Step 4b: the budget's range is now 1 to 4. Set it to 1 as written; the queue behaviour is the same.
- Step 6: deletion is now offered (step 8 below), so the last sentence's expectation that no deletion affordance appears no longer holds. In the real-cluster session, delete one object you uploaded during the session, and check it is gone and recorded; do not run the bulk deletions of step 8 against the real cluster.

## 8. Deletion (0.2.0)

Against SAIO or a test container.

8a. One object. Select an object and delete it. Expected: the dialog names the object and asks for confirmation; after it, the object is gone (`swift stat` reports not found), and "Recent changes" holds the deletion.

8b. A selection. Select several loaded rows and delete them as one job. Expected: the preview names how many it will delete; the job deletes exactly those; the job's Item details list each one.

8c. A marker and a manifest. Delete a prefix marker, and a large object's manifest without its segments, by unticking "Also delete the segments" in its dialog first. Expected: the marker goes and the objects under the prefix stay; the manifest goes and its segment objects stay, which the dialog says once the option is unticked.

8d. A prefix and a container. Delete every object under a prefix, then empty a container, then delete an empty container, each from its own action ("Delete prefix…", "Empty container…", "Delete container…") and with the typed confirmation its dialog asks for: the container and the prefix for a prefix (for example `testing/files/`), `empty` and the container name to empty a container (for example `empty testing`), and `delete` and the container name to delete one (for example `delete testing`). Expected: each dialog names its one job and offers no other; the preview counts what it will delete; a wrong confirmation, including the container name alone for any of the three, and `empty testing` typed to delete the container, is refused; each job ends with the counts it previewed; "Recent changes" holds each job.

8e. A changed object is deleted with the rest. Preview a prefix deletion, then overwrite one object under it from outside the application (`swift upload`), then start. Expected: the dialog says that whatever a name holds when the job runs is what goes; every object under the prefix is deleted, the overwritten one included; the job completes, and its Item details list each one as "Deleted.".

8f. Segments, deliberately. In Backstage, delete a large object together with its segments through the force path. Expected: it needs Backstage force and the typed name, the dialog says ownership is advisory, and afterwards the manifest and the segments it named are gone.

## 9. A job interrupted by the application closing (0.4.0)

Start a download of the large prefix and quit the application while it runs (the window's close button). Restart.
Expected: the application starts normally and the jobs drawer discloses the interrupted job, saying what it knows about what was and was not done; dismissing the disclosure keeps the job's record.

## 10. Settings backup and restore (0.4.0)

Open Settings from the gear at the foot of the bookmark rail and, under Backup and restore, press "Back up settings…" and save the file; then restore it into a fresh profile (an empty `XDG_DATA_HOME`, for example) with "Restore settings…" there.
Expected: the bookmarks and application settings come back, and no credential is in the file (`grep` it for the key you used) or restored: each restored bookmark shows no saved key until you enter one.

## 11. Accounts (0.5.0)

11a. Account metadata. Edit an account metadata value and save. Expected: `swift stat` shows the new value, and "Recent changes" holds the write.

11b. The account inspector. Expected: a "Storage policies" card lists what the account holds under each policy it uses, and a "Raw headers" card starts closed; opened, it shows the account's headers with any TempURL key values replaced by `[redacted]`. The container and object panes' raw headers also start closed.

11c. Keystone v3. Create a bookmark with the Keystone v3 auth type, the identity's domain, project and region, and connect. Expected: it connects and browses as a TempAuth bookmark does. If no Keystone endpoint is available, record not run.

## 12. Container features (0.5.0)

12a. TempURL keys. Set a container TempURL key, then rotate it to the second slot. Expected: `swift stat` shows the keys; the inspector's raw headers show them redacted.

12b. CORS. Set allowed origins on a container and save. Expected: `swift stat` shows the allowed origins written (it prints the header as `Meta Access-Control-Allow-Origin`).

12c. Versioning. On a container with legacy versioning (`X-Versions-Location` or `X-History-Location`), open its settings. Expected: the mode and the archive container are shown; on the archive container, the bulk-delete preview of step 8d names the container that archives into it.

## 13. Directory upload (0.5.0)

Press `Choose folder…` and pick a folder holding nested files, a symbolic link and an empty directory.
Expected: the summary names the folder and counts the skipped link and the empty directory, and the report names the first paths skipped; the upload creates each regular file under the prefix with its relative path; a folder of more than 10,000 files is refused at the pick with its count.

## 14. Pause, resume and concurrent jobs (0.5.0)

With the budget at its default of two, start three downloads of prefixes of more than 500 objects.
Expected: two run and the third queues. Pause one running download: its row says it pauses when the current batch finishes (unless that batch is its last, when it finishes instead), and it parks there; the queued job then starts. Resume the paused one: it continues from where it parked and completes with every object verified. Each job's Item details are complete, and no download's stage directory holds another job's files.

## 15. Per-job settings on uploads and downloads

Open the upload dialog and, under "Per-job settings", choose the Aggressive profile and set Transfers to 6, then upload a few files; repeat for a download, which offers no chunk size.
Expected: each job's details in the drawer show its profile as aggressive, transfers 6 "set for this job", checkers "from profile" and the buffer size "default"; the upload also shows its chunk size "calculated", and the download shows no chunk size.

## 16. Settings

Open Settings from the gear at the foot of the bookmark rail.
Expected: one view holds General (the default performance profile), Jobs, Browsing and network, Records (job history and audit trail retention) and Backup and restore, each setting on its own row with its note beneath it; the jobs drawer holds no settings.
Change the default profile to Balanced, open the upload dialog, and check its Profile starts at Balanced; set it back.

## 17. Identity and the application log

Open the About dialog. Expected: it shows the version, the full source revision and whether the tree was clean, matching `aeronautes --version`.
Start the application with `AERONAUTES_LOG_FILE=<a path>` set (ADR 0099 writes no log file otherwise), run one download, quit, and check that the file holds the session's start and that job at the default level, with no credential in it (`grep` for the key).

## 18. The main screen after the test-run fixes

These steps cover what the first candidate's run changed.

18a. The working list. Open a container, then a prefix inside it. Expected: Prefix, Filter and "Find in container" on the first row; Upload…, "Download container…" and "Copy container…" (inside a prefix, "Download folder…" and "Copy folder…") first on the second with "Count objects" quieter after them, a small circular arrow at the right of the path, whose tooltip begins "Refresh", and the deletions on a row of their own at the right: "Delete prefix…" inside a prefix or with one folder selected alone, and "Empty container…" and "Delete container…" at the top otherwise.
Click an object, then another, then hold Ctrl and click a third. Expected: the buttons' labels follow the selection and "Delete object…" or "Delete selected…" appears with the deletions, but no button changes place and the list of objects does not move. Press Escape: nothing is selected, and the buttons name the container or folder again.

18b. The inspector and status bar. Expected: an ordinary container shows no "Segment classification" card; the TempURL card says in one line that either key signs temporary URLs, with the rotation steps under "How to rotate a key"; the status bar says "connected to" and the bookmark's name, and the About link reads "Aeronautes" and the version.

18c. A job from a dialog. Start a copy, then press "Show in jobs" in the dialog, with the drawer's account filter first set to another account. Expected: the dialog closes and the drawer opens on the Jobs tab with the copy's row expanded and the filter back on all accounts.

18d. The drawer. Expected: the recovery notice is one line, giving the count of records and jobs and saying what they track is unchecked, with the rest under "Details"; a finished job holding records says "1 recovery record" (or the count) under its counts; rows alternate in tint. On a failed job, its error is one line in the row and whole in the row's details, and "Copy details" there puts the job's facts and error on the clipboard (paste them into a text editor).

18g. A selected folder. At a container's top level, select a folder row and press the delete button. Expected: the button reads "Delete prefix…", and the dialog is headed "Delete prefix" for that folder, offers no choice of another job, and arms only on the container and folder typed (for example `testing/files/`).

18h. A copy up to the top. Copy `testing/files/` to the same bookmark and container `testing` with the destination folder path cleared; it starts as `files/` (step 19o). Expected: the preview counts the files, the copy completes, and the files appear at the top of `testing` beside `files/`, which still holds the originals; when `files/` was made in the application, its marker stays in `files/` and nothing named `files/` or empty appears at the top, and the container's own settings are unchanged. Copying the top of `testing` into `files/` is still refused as an overlap.

18e. A copy overlap. Open the container `testing` at its top, press "Copy container…", and preview a copy to the same bookmark, the container `testing` and the destination folder path `inner/`. Expected: the refusal says in plain words that the destination, prefix "inner/" of container "testing", is inside the source, the whole of container "testing", and how to avoid it.

18f. A failed upstream. With `AERONAUTES_LOG_FILE` set, start a copy, then make the store unreachable (for example take the network down) before it finishes. Expected: the job fails, and the log holds a "storage gateway" warning naming the host and the network error, with no token, account path or object name in it. This step may be recorded as not run if the store cannot be made unreachable safely.

## 19. Added for the final candidate

These steps cover what 0.5.0 gained after the first candidate's run.

19a. Where the files are.
Quit the application, make two empty directories, and start it with `XDG_CONFIG_HOME` and `XDG_DATA_HOME` set to them, which leaves the profile of steps 1 to 18 untouched.
Create a bookmark with a test account's key, change one setting in Settings, then delete the bookmark, so its key leaves the keyring, and quit.
Expected: `<config>/aeronautes/settings.json` holds the setting as readable JSON; `<data>/aeronautes/aeronautes.sqlite` exists; neither holds the key (`grep` both for it); bookmarks from a development build's `~/.local/state/aeronautes/state.sqlite`, if one is present, did not appear.
Start the application again without the two variables: it opens the profile of steps 1 to 18 as before.

19b. A selection.
In a container, select three objects, then press "Download selected…" and download them; then "Copy selected…" to another container.
Expected: each preview counts the three objects, and only those three are downloaded and copied.

19c. Switching accounts.
With two bookmarks, connect to one and find a container that shows a badge, such as the versioned container of step 12c or the container given CORS in step 12b, switch to the other bookmark, then switch back.
Expected: each switch shows that bookmark's containers and the status bar names it; after switching back, that container's badge shows its current setting, and its tooltip names the setting and says when it was observed.
Whether a switch reused the earlier sign-in is not judged by eye: the application shows nothing that tells the two apart, and the automated tests cover it.

19d. Keystone discovery and IDs.
On the bookmark of step 11c, remove the trailing `/v3` from the Identity URL and connect; then fill User ID and Project ID with the identity's IDs, clear Username and Project, and connect; then set the Identity URL to an address that offers no Keystone v3, such as the storage URL, and connect.
Expected: the first two connect and browse; the third is refused with a message that the Identity URL "does not offer Keystone v3 at the same address" and an example ending in `/v3`.
If no Keystone endpoint is available, record not run.

19e. Importing bookmarks.
Write an rclone.conf holding two Swift remotes for test accounts, one with the right key and one with a wrong key.
In Settings, press "Import bookmarks…" and choose the file, leave "Verify after import" ticked, and import both.
Expected: the dialog names the file and says passwords stay in the credential store and are never shown; a remote that matches an existing bookmark starts unticked and says why; after the import one row reads "Imported and verified." and the other "Imported, but did not verify:" with a plain reason; the rail shows a "!" flag on the second, whose tooltip begins "Did not verify"; entering the right key in its editor and verifying clears the flag; no key is in `settings.json`, the database or the log (`grep` each).
If a clouds.yaml with a `secure.yaml` beside it is available, import it the same way; record that part as not run otherwise.

19f. Context menus.
Right-click an object row, a folder row and a container in the container column.
Expected: each menu offers the toolbar's own actions for that row: for an object, "Download object…", "Copy object…", "Copy name" and "Delete object…"; for a folder, "Open", "Download folder…", "Copy folder…", "Copy name" and "Delete prefix…"; for a container, "Open", "Upload…", "Download container…", "Copy container…", "Copy name", "Empty container…" and "Delete container…".
Each opens the same dialog as the toolbar, and "Copy name" puts the name on the clipboard.

19g. A copy's destination.
At a container's top, press "Copy container…", choose the other bookmark as the destination, and type into the destination container field; then type a container name that bookmark does not hold and preview.
Expected: the field suggests that bookmark's containers; the preview says the container "does not exist on" that bookmark and offers "Create container <name> on <bookmark>", with Start copy disabled; pressing it creates the container on that bookmark (`swift list` there), the preview runs again, Start copy is enabled, and "Recent changes", with no bookmark filter set, holds the create.

19h. The "/" folder.
In a container made for the test, upload a folder into the prefix `/` (type `/` in the Prefix field first), then open the container's top.
Expected: the top lists a `/` folder, and opening it shows the uploaded folder.
On a Ceph RGW store, whose own listing leaves that folder out, the same is expected; record which store was used.

19i. Segmented uploads.
Upload a file larger than the chunk size; lowering the chunk size under "Per-job settings" keeps the file small.
Expected: the upload dialog says files larger than the chunk size upload as static large objects, and the inspector shows the uploaded object as a Static Large Object (SLO).
On a store that does not offer static large objects that Aeronautes can read back, the dialog says the upload is a dynamic large object and why.
A bookmark set to "Dynamic large objects" under "Segmented uploads" uploads a Dynamic Large Object (DLO).

19j. Possible backstage.
On a test account, press "+" beside "Containers" and create a container whose name ends in `_segments`, then upload one small file into it.
Expected: the new container opens with this notice above its listing: "This container is named like a segment store. Objects here may be segments of larger objects, and deleting one can break the object it belongs to."
In the Logical view its row is not among the containers until the heading "Possible backstage · N", shown in capitals, is pressed; N counts it, its row is drawn in muted text, and pressing the heading again closes the group.
Right-click the file and choose "Delete object…", then press "Empty container…": each dialog shows the same notice.
Cancel the first and close the second, so nothing is deleted.
An ordinary container shows the notice in neither place.

19k. The container list after a change made elsewhere.
With the application connected to a test account, create a container on that account with another tool (`swift post <name>`), without touching the application.
Expected: the Containers column does not show it; pressing the circular arrow beside "Containers", whose tooltip begins "Refresh", shows it, and the other rows stay on screen while the list is read.
Then delete that container with the other tool (`swift delete <name>`), use another window for more than thirty seconds, and click back into the application.
Expected: the container leaves the column without anything being pressed.

19l. Duplicating a bookmark.
Open a saved bookmark's editor with the "✎" beside it on the rail and press "Duplicate…".
Expected: an "Add bookmark" form opens, named with the first bookmark's name followed by "copy" and filled with its details; the key field is empty, and a note says what it was copied from and that a key is never copied.
Change the user, and the project if it differs, to a second test account's, enter that account's key and press "Save & connect".
Expected: the second account connects under the new bookmark, and the first bookmark still connects as before.
If the first bookmark uses a custom CA, the note also asks for the CA bundle again; if it has a storage URL override, as a bookmark imported from an rclone remote with a `storage_url` does, the note says the override was not copied.
Record whether either was tried.

19m. Import from the rail, names, and a bookmark with no key.
Write an rclone.conf holding two Swift remotes for a test account, one with its `key` line and one without, and press "Import" on the rail, under "Add".
Expected: the preview of step 19e opens, and each row that can be imported has a name field holding the remote's name.
Change the first row's name, tick both rows and import.
Expected: the summary offers "Enter key" on the second row; the rail shows the first bookmark under the name typed, and the second with a "!" whose tooltip begins "No saved key".
Press "Copy container…" in any container: the destination list shows the second bookmark as "(no saved key)" and it cannot be chosen.
Click the second bookmark on the rail.
Expected: its editor opens, saying it has no saved key, with the cursor in the key field; no connection is attempted.
Enter the key and press "Save & connect": it connects and the "!" is gone.
On the empty profile of step 19a, the welcome dialog offers "Import bookmarks…", which opens the same file picker; record not run if that profile was not kept.

19n. What a container deletion leaves.
In a container made for the test, upload a file larger than the chunk size as in step 19i, then press "Delete container…".
Expected: the dialog says a container named after this one, ending in `_segments`, exists, with its object count and size.
Preview.
Expected: "Also delete the segments of large objects" is ticked, and the notice says this deletion also deletes the segments of its large objects.
Untick it.
Expected: the notice says a deletion here removes nothing from that container.
Type `delete` and the name, as the dialog asks, and delete.
Expected: when the job is done the dialog stays open, says the `_segments` container still exists and that the deletion removed nothing from it, and offers "Open that container".
Press it: that container opens, with the notice of step 19j above its listing.
The test's only large object is gone, so nothing else uses what is there: delete that container the same way, and check with `swift list` that neither container remains.

19o. A folder copies as a folder.
In a container made for the test that holds a folder with a few objects in it, select the folder's row and press "Copy folder…".
Expected: the destination folder path already holds the folder's name with its slash, and the destination scope line shows it.
Enter another container made for the test, preview and start the copy.
Expected: that container holds the folder under its own name, with the objects inside it, and none of them at its top.
Open the folder itself, press "Copy folder…" and expect the same starting path; for a whole container, and for an object or a selection of objects, the path starts empty.

19p. Segments deleted with their objects.
In a container made for the test, upload three files larger than the chunk size as in step 19i, two into a folder and one at the top, and note with `swift list` what the `_segments` container holds.
Open the folder, select one of its files and press "Delete manifest…".
Expected: "Also delete the segments" is ticked, the dialog asks for the object's name, and "Delete manifest + segments" stays disabled until the name is typed.
Type the name and delete.
Expected: the job completes, its Item details list the manifest and each segment, and `swift list` shows the `_segments` container no longer holds that file's segments and still holds the other two files'.
Select the folder and press "Delete prefix…", then preview.
Expected: under the preview, "Also delete the segments of large objects" is offered and is ticked, the dialog says that each large object's segments are deleted after it and that it cannot show another object does not use them, and the text to type is the container and the folder followed by `and segments`.
Untick it.
Expected: the text to type is the container and the folder alone, what was typed before is cleared, and the dialog says the deletion is manifest-only.
Preview again: the option is ticked again.
Type the words and delete.
Expected: the job completes and `swift list` shows the `_segments` container holds only the segments of the file at the top.
Press "Delete container…", preview, type the words and delete.
Expected: the container is gone, the remaining segments are gone, and the dialog stays to say the `_segments` container still exists; open it and delete it as in step 19n.
Steps 8c and 19n untick the option, and cover what a deletion without it leaves.

19q. Large objects where the container keeps versions.
This needs a store with `versioned_writes`, as SAIO has; record it as not run otherwise, which does not block the tag.
Make two containers for the test, and in the first press "Configure container", set Versioning to "history location" with the second as its archive container, and save.
Upload a small file and two files larger than the chunk size into the first, and note what its `_segments` container holds.
Expected: the upload dialog says the large files upload as dynamic large objects because this container keeps versions, and the inspector shows each as a Dynamic Large Object (DLO) with a metadata key `Mtime`.
The second container holds nothing yet: an upload writes each file at its name and stages nothing.
Select the small file and press "Delete object…".
Expected: the dialog says the container keeps history in the second container; after the delete the file is gone from the first and `swift list` shows it in the second, under a name that starts with three hex digits and the file's name, beside a zero-byte marker.
Select one large file and press "Delete manifest…".
Expected: no option to delete its segments is offered, and the dialog says its segments cannot be deleted with it here because the container keeps versions; after "Delete manifest only" the second container holds a version of it and the `_segments` container holds what it held before.
Press "Delete container…" and preview.
Expected: the option is not offered and the dialog says a kept version still uses its segments; after the deletion the first container is gone, the second holds a version of the other large file, and the `_segments` container is unchanged.
Open the second container, press "Delete container…" and preview.
Expected: the option is offered and ticked, because no container keeps its versions there any more; after typing the words and deleting, the second container is gone and the `_segments` container is empty; delete that as in step 19n.

19r. Folders in a selection.
Open a container or folder that lists at least two folders and a file; nothing is copied or downloaded in this step.
Select the file and one folder together and press "Copy selected…".
Expected: a warning opens before the copy dialog, headed "1 selected folder will not be copied"; it names the folder, says that it and everything in it will not be copied, and says how to copy everything: select the folder alone, or close the warning and press Escape to clear the selection.
Press "Cancel". Expected: no dialog is open.
Press "Copy selected…" again and then "Copy the 1 object only…". Expected: the copy dialog opens with the one file as its source and a line saying one selected folder is not included; close it.
Press "Download selected…". Expected: the same warning, for a download; cancel it.
Select the two folders alone and press "Copy selected…". Expected: the warning says several folders cannot be copied in one go yet and offers only "Close".

19s. A copy writes in place and replaces only what you confirm.
Make two containers for the test.
Upload a small file and a larger one into the first with the chunk size set below the larger file's size, and with "Edit metadata" give each a key of its own.
Copy the first container to the second with the same chunk size.
Expected: the job ends complete; in the second container each object shows its key, the large one is a Dynamic Large Object (DLO) that downloads whole, and no name there or in the second container's `_segments` container contains `.aeronautes/stage/`.
Preview the same copy again, with the same chunk size.
Expected: the preview counts the small object as unchanged and the large one as uncertain, and after "Start copy" the job ends complete with nothing copied: a large object is skipped when the store reports the same size and tag for both, which the same chunk size gives.
Replace the small file in the first container by uploading a different file of the same name, then preview the copy again without pressing "Replace existing objects…", and start it.
Expected: the job ends partial with one overwrite refused, and the second container's object is unchanged.
Preview once more, press "Replace existing objects…" and then "Start copy".
Expected: a native dialog names both accounts, the second container and the one object, and says what happens to a replaced large object's old segments; declined, nothing is written and no job starts; confirmed, the job ends complete with the object replaced.

## Results

Record one row per step in `0.5.0-test-results.md` beside this plan: step, observed, pass or fail, evidence.
The plan passes when every step passes or is recorded as not run where this plan allows it; a failure is a finding for the author before the tag.
