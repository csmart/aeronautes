# 0.5.0 test plan

Written on 11 November 2026 for the operator's decision of the same day to cut 0.5.0 as the first tagged release, with its Linux packages published on GitHub, after the operator has run this plan against the release candidate.
It supersedes the [0.1.0 test plan](../2026-09-24/0.1.0-test-plan.md), which was never run: its steps 1 to 7 are carried here with the changes stated, and steps 8 to 17 cover what 0.2.0 to 0.5.0 added and the fixes from the first test run.
Every step is run by the operator on a Linux workstation; none of it can be driven headless, which is why these checks are here rather than in CI.
A failed step blocks the tag ([RELEASING](../../RELEASING.md)).
Results go in `0.5.0-test-results.md` beside this plan, one row per step: what was observed, pass or fail, and where the evidence is (log path or screenshot).
Where an expected sentence below is quoted, record the exact text if the application's differs; a different wording is a note, a different meaning is a finding.

## Before starting

- The candidate is the Linux packages a release-workflow dispatch builds from the commit to be tagged; the author downloads them into the evidence packet and names the directory. They report the version `dev` with the commit's full revision; the tag build of the same commit stamps `v0.5.0`.
- The 0.1.0 plan's "Before starting" applies, with one change: the active-job budget now defaults to two and allows four.
- Steps 8 and 14 delete and pause real objects and jobs: run them against SAIO or containers made for the test, never against data that matters.
- Step 11c needs a Keystone v3 endpoint; if none is available, record it as not run, which does not block the tag.
- Run the application from a terminal so its output is retained, and keep the jobs drawer's "Recent changes" tab in view when a step says so.

## Steps 1 to 7, carried from the 0.1.0 plan

Run steps 1 to 7 of the [0.1.0 plan](../2026-09-24/0.1.0-test-plan.md) as written, with these changes.

- Step 1: the rpm under test is the 0.5.0 candidate's. If an Ubuntu 24.04 host is available, also install the candidate deb there (`sudo apt install ./<name>.deb`), run `aeronautes --engine` and `aeronautes --version`, and remove it; record it as not run otherwise.
- Step 4: the settings it names are in the Settings view, opened from the gear at the foot of the bookmark rail, not in the jobs drawer; the notes and statuses beside each are worded as the view shows them.
- Step 4b: the budget's range is now 1 to 4. Set it to 1 as written; the queue behaviour is the same.
- Step 6: deletion is now offered (step 8 below), so the last sentence's expectation that no deletion affordance appears no longer holds. In the real-cluster session, delete one object you uploaded during the session, and check it is gone and recorded; do not run the bulk deletions of step 8 against the real cluster.

## 8. Deletion (0.2.0)

Against SAIO or a test container.

8a. One object. Select an object and delete it. Expected: the dialog names the object and asks for confirmation; after it, the object is gone (`swift stat` reports not found), and "Recent changes" holds the deletion.

8b. A selection. Select several loaded rows and delete them as one job. Expected: the preview names how many it will delete; the job deletes exactly those; the job's Item details list each one.

8c. A marker and a manifest. Delete a prefix marker, and a large object's manifest without its segments. Expected: the marker goes and the objects under the prefix stay; the manifest goes and its segment objects stay, which the dialog says beforehand.

8d. A prefix and a container. Delete every object under a prefix, then empty a container, then delete an empty container, each with the typed confirmation the dialog asks for: the container and the prefix for a prefix (for example `testing/files/`), the container name for a container. Expected: the preview counts what it will delete; a wrong confirmation, including the container name alone for a prefix, is refused; each job ends with the counts it previewed; "Recent changes" holds each job.

8e. A changed object is not deleted. Preview a prefix deletion, then overwrite one object under it from outside the application (`swift upload`), then start. Expected: that object is refused as changed since listed and is still there afterwards; the others are deleted; the job is partial and says why.

8f. Segments, deliberately. In Backstage, delete a large object together with its segments through the force path. Expected: it needs Backstage force and the typed name, the dialog says ownership is advisory, and afterwards the manifest and the segments it named are gone.

## 9. A job interrupted by the application closing (0.4.0)

Start a download of the large prefix and quit the application while it runs (the window's close button). Restart.
Expected: the application starts normally and the jobs drawer discloses the interrupted job, saying what it knows about what was and was not done; dismissing the disclosure keeps the job's record.

## 10. Settings backup and restore (0.4.0)

Open Settings from the gear at the foot of the bookmark rail and, under Backup and restore, press "Back up settings…" and save the file; then restore it into a fresh profile (an empty `XDG_DATA_HOME`, for example) with "Restore settings…" there.
Expected: the bookmarks and application settings come back, and no credential is in the file (`grep` it for the key you used) or restored: each restored bookmark shows no saved key until you enter one.

## 11. Accounts (0.5.0)

11a. Account metadata. Edit an account metadata value and save. Expected: `swift stat` shows the new value, and "Recent changes" holds the write.

11b. The account inspector. Expected: a "Storage policies" card lists what the account holds under each policy it uses, and a "Raw headers" card starts closed; opened, it shows the account's headers with any TempURL key values replaced by `[redacted]`. The container and object panes' raw headers also start closed.

11c. Keystone v3. Create a bookmark with the Keystone v3 auth type, the identity's domain, project and region, and connect. Expected: it connects and browses as a TempAuth bookmark does. If no Keystone endpoint is available, record not run.

## 12. Container features (0.5.0)

12a. TempURL keys. Set a container TempURL key, then rotate it to the second slot. Expected: `swift stat` shows the keys; the inspector's raw headers show them redacted.

12b. CORS. Set allowed origins on a container and save. Expected: `swift stat` shows the allowed origins written (it prints the header as `Meta Access-Control-Allow-Origin`).

12c. Versioning. On a container with legacy versioning (`X-Versions-Location` or `X-History-Location`), open its settings. Expected: the mode and the archive container are shown; on the archive container, the bulk-delete preview of step 8d names the container that archives into it.

## 13. Directory upload (0.5.0)

Press `Choose folder…` and pick a folder holding nested files, a symbolic link and an empty directory.
Expected: the summary names the folder and counts the skipped link and the empty directory, and the report names the first paths skipped; the upload creates each regular file under the prefix with its relative path; a folder of more than 10,000 files is refused at the pick with its count.

## 14. Pause, resume and concurrent jobs (0.5.0)

With the budget at its default of two, start three downloads of prefixes of more than 500 objects.
Expected: two run and the third queues. Pause one running download: its row says it pauses when the current batch finishes (unless that batch is its last, when it finishes instead), and it parks there; the queued job then starts. Resume the paused one: it continues from where it parked and completes with every object verified. Each job's Item details are complete, and no download's stage directory holds another job's files.

## 15. Per-job settings on uploads and downloads

Open the upload dialog and, under "Per-job settings", choose the Aggressive profile and set Transfers to 6, then upload a few files; repeat for a download, which offers no chunk size.
Expected: each job's details in the drawer show its profile as aggressive, transfers 6 "set for this job", checkers "from profile" and the buffer size "default"; the upload also shows its chunk size "calculated", and the download shows no chunk size.

## 16. Settings

Open Settings from the gear at the foot of the bookmark rail.
Expected: one view holds General (the default performance profile), Jobs, Browsing and network, Records (job history and audit trail retention) and Backup and restore, each setting on its own row with its note beneath it; the jobs drawer holds no settings.
Change the default profile to Balanced, open the upload dialog, and check its Profile starts at Balanced; set it back.

## 17. Identity and the application log

Open the About dialog. Expected: it shows the version, the full source revision and whether the tree was clean, matching `aeronautes --version`.
Start the application with `AERONAUTES_LOG_FILE=<a path>` set (ADR 0099 writes no log file otherwise), run one download, quit, and check that the file holds the session's start and that job at the default level, with no credential in it (`grep` for the key).

## 18. The main screen after the test-run fixes

These steps cover what the first candidate's run changed.

18a. The working list. Open a container, then a prefix inside it. Expected: Prefix, Filter and "Find in container" on the first row; Upload, Download and "Copy to" first on the second, Refresh and "Count objects" quieter after them, and the deletion at the right, named "Delete prefix…" inside a prefix and "Empty or delete container…" at the top.

18b. The inspector and status bar. Expected: an ordinary container shows no "Segment classification" card; the TempURL card says in one line that either key signs temporary URLs, with the rotation steps under "How to rotate a key"; the status bar says "connected to" and the bookmark's name, and the About link reads "Aeronautes" and the version.

18c. A job from a dialog. Start a copy, then press "Show in jobs" in the dialog, with the drawer's account filter first set to another account. Expected: the dialog closes and the drawer opens on the Jobs tab with the copy's row expanded and the filter back on all accounts.

18d. The drawer. Expected: the recovery notice is one line, giving the count of records and jobs and saying what they track is unchecked, with the rest under "Details"; a finished job holding records says "1 recovery record" (or the count) under its counts; rows alternate in tint. On a failed job, its error is one line in the row and whole in the row's details, and "Copy details" there puts the job's facts and error on the clipboard (paste them into a text editor).

18g. A selected folder. At a container's top level, select a folder row and press the delete button. Expected: the button reads "Delete prefix…", and the dialog offers "Delete prefix" for that folder by default with the two container modes below it, and arms only on the container and folder typed (for example `testing/files/`).

18h. A copy up to the top. Copy `testing/files/` to the same bookmark and container `testing` with the destination folder path left empty. Expected: the preview counts the files, the copy completes, and the files appear at the top of `testing` beside `files/`, which still holds the originals. Copying the top of `testing` into `files/` is still refused as an overlap.

18e. A copy overlap. Open the container `testing` at its top, choose "Copy to", and preview a copy to the same bookmark, the container `testing` and the destination folder path `inner/`. Expected: the refusal says in plain words that the destination, prefix "inner/" of container "testing", is inside the source, the whole of container "testing", and how to avoid it.

18f. A failed upstream. With `AERONAUTES_LOG_FILE` set, start a copy, then make the store unreachable (for example take the network down) before it finishes. Expected: the job fails, and the log holds a "storage gateway" warning naming the host and the network error, with no token, account path or object name in it. This step may be recorded as not run if the store cannot be made unreachable safely.

## Results

Record one row per step in `0.5.0-test-results.md` beside this plan: step, observed, pass or fail, evidence.
The plan passes when every step passes or is recorded as not run where this plan allows it; a failure is a finding for the author before the tag.
