# 0.1.0 test plan

Written on 24 September 2026 for the operator's decisions 19 and 20 in the [Linux finish line](../2026-09-05/linux-finish-line.md): the first release is 0.1.0, and it is cut only after the operator has run this plan against the release candidate.
Every step is run by the operator on a Linux workstation; none of it can be driven headless, which is why these checks are here rather than in CI.
A failed step blocks the tag ([RELEASING](../../RELEASING.md)).
Results go in a results record beside this plan, one row per step: what was observed, pass or fail, and where the evidence is (log path or screenshot).

## Before starting

- Build the candidate from the commit to be tagged: CI's Linux artifacts, or `wails3 task linux:create:rpm` locally. The rpm is named `aeronautes-<version>-linux-amd64-UNSIGNED.rpm`; `aeronautes --version` prints the stamped version and source revision.
- Step 1 needs a Fedora 44 host with podman outside any toolbox (a toolbox user namespace maps a single id, so package installs that chown to service users fail there).
- Steps 2 to 5 need a desktop session with a Secret Service keyring and a Swift account with a container of more than 1,000 objects and a prefix of more than 500 objects; the SAIO used by the tests is enough. Steps 2a-ii and 2a-iii also need a few local files to send, one of them sharing a name with an object already under the chosen prefix, and 2a-iii is worth running once more against a large object's manifest so the question's segment sentence can be checked. Step 6 needs the real target cluster.
- Run the application from a terminal so its output is retained, and keep the jobs drawer's "Recent changes" tab in view when a step says so: it lists the audit trail.

## 1. Install on a clean host

Run, outside the toolbox:

```
sh /home/csmart/code/.aeronautes-work/20261026-engine-bundle/install-test-host-command.sh <directory holding exactly one aeronautes rpm>
```

The argument names the directory holding the candidate rpm and nothing else of that name. The script installs the rpm into a fresh Fedora 44 container, verifies it, runs the binary's engine report and version, and removes it, writing `install-test-host-run.log` beside itself; it exits non-zero as soon as any step fails, including a failed or partial `dnf` transaction, so its exit status is the gate. Run it where rootless podman has subordinate id ranges (or as root): a single-id user namespace cannot chown the files of unrelated dependencies, the transaction then fails, and the run stops there rather than reporting application checks after a partial install. On a host without those ranges, a second argument `--allow-partial-transaction` lets the run continue into the application checks, and its final line is then labelled QUALIFIED: evidence about this package and its engine, not about a clean install.
Expected in that log: the rpm and its declared dependencies (gtk4 and webkitgtk6.0; no rclone package, because the rpm carries its own engine under [ADR 0089](../../adr/0089-bundled-engine-on-linux.md)) install from the Fedora repositories and `dnf` exits 0; `rpm -V clean` is printed; `aeronautes --engine` reports rclone v1.74.3 as a verified sidecar at `/usr/local/libexec/aeronautes/rclone` and exits 0; `aeronautes --version` prints the stamped identity; the `ldd` count of missing libraries is 0; after removal `rpm -q aeronautes` reports the package is not installed. The binary has no help flag: without a display it can only answer `--version` and `--engine`. Run `aeronautes --version` on the installed binary of a desktop host as well, to see the stamped version and revision.
The toolbox run of 24 September 2026 passed every application check but exited non-zero because five unrelated packages (polkit, polkit-pkla-compat, cups-filesystem, geoclue2, usbmuxd) could not chown in the single-id namespace; the host run is the clean form.
Record the log path.

## 2. Native journey (ADR 0073 option B)

2a. Chooser title. Connect a bookmark, open a container, select a prefix and start a download. The native directory chooser's title reads `Download from <bookmark display name> (<account>), <container>/<prefix> into…`, where `<account>` is the account segment of the storage URL. A bookmark without a display name shows the account alone; with neither, "the connected account". Control characters in a name show as `?`, and a long name is cut with `…`.

2a-ii. Upload chooser title. Upload joined the release on 16 October 2026 ([ADR 0052](../../adr/0052-v1-capability-gate.md) decision 9), and its picker is the other half of 2a: no CI job can operate a native file chooser, so this step is the only product-level check of it. With a container open and a prefix selected, press `Upload…`. The chooser's title reads `Upload into <bookmark display name> (<account>), <container>/<prefix> — choose files…`, with the same account-suffix, control-character and truncation rules as 2a. Pick two or three files and start the upload.
Expected: the job completes, the objects appear under that prefix on the cluster (`swift list <container> --prefix <prefix>`), each one's size and MD5 match the local file (`swift stat` against `md5sum`), and "Recent changes" holds one entry per object.

2a-iii. Replacing what is live, which is the other native surface no CI job can operate ([ADR 0081](../../adr/0081-upload-overwrite-acknowledgement.md) decision 2: the question that authorises a replacement is raised by the application, not by the page). Pick a file whose name matches an object that already exists under the prefix and press `Upload…` again.
Expected, in this order: the dialog reports `Rejected — nothing was written`, names that object with `exists`, and offers `Replace 1 existing object…` and no way to start. It also says the application will ask you to confirm on its own dialog, not on the page. Press that button; the report comes back with the collision as a warning rather than a rejection and says the upload will REPLACE what is at 1 name. Press `Start upload`.
A native question titled `Replace 1 object?` appears. Check every part of it against the cluster: it names the count, the destination as `<container>/<prefix>`, the bookmark and its account suffix in their own right, the object name, what the container reports about versioning, and what will happen to the segments of anything large being replaced. Its buttons are `Keep what is there` (the default and the cancel button) and `Replace`.
Answer `Keep what is there`, then repeat and press Escape, then repeat and close the dialog. Each time: nothing is written, the live object is unchanged (`swift stat` gives the same entity tag and length), and the job reports a refusal rather than a failure. Only then repeat and answer `Replace`.
Expected after `Replace`: the job completes, the object's entity tag and length on the cluster match the local file, "Recent changes" holds the replacement, and if the object was a large object its segment objects are gone once the replacement verified — unless the container keeps versions or reclaiming is turned off in the jobs drawer, which the question will have said. Record the exact dialog text if it differed from the above, and record what each refusal did. A replacement that happened without the native question, or a refusal that wrote anything, is a failure and a finding before the tag.

2b. Public read. Open a container's settings, tick public read and save. A native question appears, titled `Make this container public?`, with the message `Anyone on the internet will be able to read every object in <container> (<account>).` on one line and `This question comes from the application, not from the page.` on the next, and two buttons, `Keep it private` (the default and the cancel button) and `Make it public`.
Expected: choosing `Keep it private`, pressing Escape or closing the dialog leaves the read ACL unchanged and the settings panel reports the refusal; choosing `Make it public` writes the ACL, the panel closes, and the container header shows the public banner (`Public: anyone with the URL can read objects in <container>`). Confirm with `swift stat <container>` that `Read ACL` is `.r:*` after the accepted case and unchanged after each refused case.
Record what each answer did, with the exact dialog text if it differed from the above.

## 3. Window close during a metadata save (L08)

Open an object's metadata editor, change a value, click save and close the window at once (the window's close button or Alt+F4, within a second).
Expected: the application exits within a few seconds, and on restart there is no lock complaint. Then check two things: the "Recent changes" tab and the object's metadata on the cluster (`swift stat <container> <object>`). Either the tab shows the write with result applied and the cluster shows the new value, or the tab shows nothing for it and the cluster shows the old value. A changed object without its record, or a record without the change, is a failure.
Repeat three times; the timing differs each time.
This is the live half of [ADR 0053](../../adr/0053-synchronous-writer-shutdown-ownership.md), whose evidence so far is on the mock transport.

## 4. Workload bounds (ADR 0074)

4a. Retention ceiling. In the jobs drawer set "Browser retention" to 1000; its status reads `keeps 1,000 rows`. Open the large container and page with "Load more" until the notice `1,000 rows loaded, the retention ceiling; narrow the prefix, use Find, or count the prefix. The ceiling is set in the jobs drawer.` replaces the button. Raise the setting to 2000: the button returns and paging continues.

4b. Queue depth. Set the active-job budget to 1 and "Queue depth" to 1 (`1 waiting at most`). Start one download of the large prefix, then a second (it queues), then a third. Expected: the third is refused with `the job queue is full: 1 job is waiting; wait for one to finish or cancel one`. Cancel the queued job; a new start is admitted and queues in its place.

4c. Connection cap. Set "Connection cap" to 1 (`1 connections per host on the next connect`), reconnect, and browse and inspect a few objects. Expected: everything still answers, only more slowly under load. The cap itself is proved by the maintained tests; this step checks that a session opens and works under the smallest value.

4d. Batched download. Download the prefix of more than 500 objects. Expected: the job completes with every object copied and verified; while it runs, the destination holds a directory named `.aeronautes-stage-<job id>` with at most one batch's files inside it, and after completion that directory is gone. The job's settings in the drawer show `bufferSize 16Mi`.

## 5. Credential cleanup (ADR 0076)

Create a bookmark with a saved key and confirm an item for it appears in the keyring (Passwords and Keys). Delete the bookmark. Expected: the item is gone, and the credential status dialog reports `No pending credential cleanup is recorded.`
If the keyring asks whether to delete and the prompt is dismissed, expected instead: the item stays, the dialog reports `Recorded key changes await cleanup.` and `The last cleanup pass stopped: the store still holds the key after answering the removal. It runs again after the next bookmark delete or key change.`; the next bookmark delete or key change removes it when the prompt is accepted.

## 6. Acceptance session against the real cluster

Against the target cluster rather than SAIO, in one sitting: connect; browse the containers and note the badges (public, web, versioning); open a large container and page it; use Find and count a prefix; download a prefix and compare a few files by size and checksum; upload a few files into a prefix and compare them back the same way, including one upload onto a name that already exists; edit an object's metadata and a container's settings, including one public-read change answered through the native question; create a container and a prefix marker.
Expected: every write appears in "Recent changes" with result applied and its own audit entry, every creation is visible on the cluster, the upload onto an existing name raises the application's own question and replaces only after it is answered yes, and no deletion affordance is offered for containers, markers or manifests (deletions are refused in v1).
This is the §57.4 smoke of [RELEASING](../../RELEASING.md) for 0.1.0.
