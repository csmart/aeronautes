# ADR 0081: upload replaces an existing object only on an acknowledged, bounded overwrite

**Status:** Accepted on 26 September 2026, extended on 27 September, decision 5 revised on 28 September. The operator accepted the residual exposure explicitly, in their words "for overwrites, we need to be able to overwrite an [object], so I have to accept that exposure", and added a requirement with it: "when an object is SLO/DLO and there is a manifest, we have to make sure that if it is overwritten that it does not leave orphaned fragments eating up the user's space". Told that this record met that requirement by refusing such a collision outright, they decided the other way on 27 September: "Make large objects overwritable, with the fragments accounted for - we need this". Decision 5 first read that as reclaiming, then as retaining, and the operator corrected it on 28 September: "I thought we _were_ going to try and clean up fragment orphans by default, and put it behind an option for the user to tweak", adding that the engine's own practice is the standard to copy. Decision 5 now reclaims by default, and records why it moved twice.
Amended on 16 November 2026 by [ADR 0122](0122-the-stores-answer-is-the-result.md) decision 3: the acknowledgement and its native confirmation stay, and the question now says what happens to a replaced large object's old segments from one read of the container and the setting; the record taken before a replacement, the comparison with what was acknowledged, and the application's own reclamation (decisions 5, 6 and 7) are no longer made, because the engine writes over the name and removes the old segments itself where that is allowed.
**Scope:** The upload route's publications in `internal/transfer/local` and their admission in `internal/app`. It lifts the [ADR 0020](0020-recovery-containment.md) transfer-overwrite refusal for that route alone, and decision 5 adds one named exception to ADR 0020's refusal of reclamation: a replaced large object's own recorded fragments, after a verified replacement, under an option. Mirror and every other ADR 0020 refusal are untouched, and no other route gains authority to reclaim anything.
[ADR 0087](0087-copy-overwrite-on-upload-terms.md) later extended the lift of the transfer-overwrite refusal to the copy route on the same terms; reclamation stays this route's alone.

## Delivery note, 16 October 2026

**Decision 2 was implemented as a seam and not as a product, for three weeks.** `OverwriteConfirmer`, `WireOverwriteConfirmer` and the refusal for a service without one were all in place and tested, and every test supplied its own answer — but `main.go` never called that wiring function, and the interface never asked either: `LocalTransferDialog` froze the request's acknowledgement to false. So the shipped build refused every replacement with "replacing an existing object needs the shell's confirmation, and this build has none", and a live destination name was a rejecting problem with nothing offered beyond it. The capability the operator enabled on 16 October 2026 could create and not replace.

That is closed in the same release. The shell question is `wailsOverwriteConfirmer` over the one native question surface `askNative` now holds for both confirmers, so "a dismissed dialog is a refusal" is written once; the sentences it shows are `app.OverwriteQuestion`, composed where they can be asserted rather than described, as ADR 0082's startup lines are; and the dialog offers the replacement only when a collision is the *whole* reason it was rejected. `TestMainWiresEverySeamTheShellMustSupply` is the check that would have caught the gap: it derives the shell's seams from the exported interfaces of `internal/app` and requires `main.go` to wire each one, because a seam that exists and is never wired is invisible to a test binary that supplies its own.

## What happens today

As of master 5446eb18, decisions 1 to 4 and 6 to 9 are implemented and decision 5 is implemented in its RETAINING form: a replaced large object's fragments are recorded and left. This revision changes that form to reclaiming and its implementation is owed. What follows describes the route before any of it, because that is what the decisions are measured against.

Upload never replaces anything, and not by accident. Every live publication carries `If-None-Match: *`, so the store refuses when the name exists and the first writer wins. The preflight also reports a live name as a rejecting problem of kind `exists` whose detail reads "already live at the destination; v1 upload never overwrites". That conditional is what satisfies ADR 0020's refusal of a transfer overwrite "until an enforceable protocol is implemented".

## What the protocol allows, measured

The [upload protocol measurements](../experiments/2026-09-25-upload-protocol-measurements.md) of 25 September 2026 settle part of this and deliberately leave the rest open.

- **Replace-if-unchanged is not available.** `If-Match` carrying a wrong entity tag was ignored and the write applied. There is no precondition on this store that binds a replacement to the object the operator looked at, so ADR 0020's enforceable protocol does not exist and this record does not supply one.
- **Create-if-absent is available.** `If-None-Match: *` was honoured with 412 and the body unchanged, so every publication that is not an acknowledged overwrite stays race-free.
- **A corrupted overwrite is refused and the prior object survives it.** An overwrite whose declared `ETag` disagreed with the body was answered 422 and the prior bytes were read back afterwards.
- **An unobserved outcome stays unknown.** The one abandoned-request observation produced no HTTP response at all, so it says nothing about a request whose body the store received completely and whose response was then lost. That case can still have replaced, and this record keeps it uncertain rather than claiming otherwise.
- **A versioned container recorded an archive entry.** On a container carrying `X-History-Location`, an archive entry with a timestamped name appeared after the second write. Its bytes were not read, so what is recorded is that the store noted a previous version, not that one is recoverable.
- **Overwriting a large object's manifest orphans its segments.** Every segment stayed listed in the segments container, referenced by nothing the application knows of.

## Decision

1. **An overwrite happens only when the operator asked for one.** `UploadRequestDTO` gains an acknowledgement field. Without it the route behaves exactly as it does today: conditional create, `exists` rejects the preflight, and a collision at commit is a conflict.
2. **The acknowledgement that authorises the replacement is raised by the backend, not supplied by the page.** As in [ADR 0073](0073-selected-resource-acknowledgement.md), the field in the request protects against an operator's accident, not against a hostile webview, because a compromised page can set it itself. Before dropping any conditional, the backend raises one native confirmation through the same seam shape as the public-ACL confirmer, wired by a package function under [ADR 0011](0011-typed-service-surface.md) and never reachable as a bridge action. No confirmation, no replacement.
3. **The confirmation names the account the backend resolved, not only the count.** ADR 0073's counterexample survives otherwise: a page can connect account B while displaying account A, every backend check legitimately binds B, and a same-named container with the same number of collisions produces an identical question. So the confirmation names the bookmark and its account suffix as the backend resolved them, the container, and the prefix, in the shape the download chooser's title already uses. The upload picker is titled the same way, which it is not today: `PickUploadFiles` still titles it "Choose files to upload".
4. **The answer authorises one plan, not a later one.** The confirmation is bound to the collision set the preflight computed and to the captured authority it was computed under. A start whose scope, account, generation or collision set differs from the one confirmed is refused rather than carried by the earlier answer.
5. **A collision whose live object is a large object is admitted on the same acknowledged terms, and its predecessor's fragments are reclaimed after the replacement is verified, under an option that defaults to reclaiming.** This decision has been written three times and this is the third; the two earlier readings are kept below because the operator is entitled to see why it moved.

   Until 27 September 2026 such a collision was rejected outright. The operator then decided they need it, and asked that the fragments be accounted for rather than left eating space. The first draft read that as reclaiming them, on the reasoning that the engine names each run with a random component so the prefix belongs to one upload. That reasoning is wrong on its own terms — the prefix is published in the live manifest's own header, so any client that can read the object can read the prefix and build its own manifest over those segments — and the second draft therefore retained everything and reclaimed nothing. The operator's answer to that, on 28 September, was that reclamation was what they had asked for and that the engine's own behaviour is the standard to copy.

   **What the engine actually does, measured.** One replacement of a **dynamic** large object by the pinned rclone v1.74.3, traced at the wire (`docs/experiments/2026-09-27-overwrite-mechanism.md`): it HEADs the object, lists the segments container under the **old** prefix, writes the new segments under a **new** prefix, PUTs the new manifest over the name, HEADs the container, issues **one account-level `DELETE ?bulk-delete=1` for the old segments**, and then HEADs the object. With `X-History-Location` set on the container the sequence is identical except that the bulk-delete does not happen at all. Both retained traces are dynamic manifests, so what is measured is that the reference implementation reclaims by default on a DLO replacement and declines to when the container keeps history. Reclaiming a **static** manifest's segments is this contract's own decision by analogy, not a measured engine behaviour, and the distinction is kept here because the analogy is the weaker of the two grounds.

   **So this contract reclaims, and states exactly what that costs.** The exposure the second draft refused to accept is real and is not removed by the engine doing the same thing: another object built over the same published prefix loses its backing data, silently, after this job's own write succeeded. What changed is not the risk but who decides. The operator has now decided twice, knowing the exposure, and the ecosystem's default behaviour is the same. A record that refuses the operator's decision on a risk they have accepted is not caution, it is the record substituting its own judgement for theirs.

   **The reclamation is bound by five rules.**

   - It runs only after the replacement is **verified**. This is a deliberate deviation from the engine, which deletes before its final read; the old bytes are not discarded until the new object is confirmed to be there.
   - It **skips entirely when the container keeps versions**, matching the engine and for the reason the second draft gave: those segments belong to a retained version, and removing them would break the archive rather than reclaim waste.
   - It removes **only what the predecessor's recorded inventory named**, by the identities recorded before the publication. Nothing is derived from a prefix at the time of deletion, and an inventory that was unread, or truncated at this build's bound, reclaims only the entries it holds and reports the rest as left behind.
   - It uses **bulk delete**, as the engine does, and records each object's own result. A partial success is reported as exactly that: the objects reclaimed, and the objects that were not. The engine's traced replacement issued one request because its segments were one prefix of one container. The protocol does not require that: a bulk-delete body carries account-level `/container/object` paths and may span containers ([bulk delete](https://docs.openstack.org/swift/latest/api/bulk-delete.html)). Sending one request **per container** is this client's own choice — `swiftcontrol.BulkDelete` addresses one container per call — and this route follows it rather than widening that client here. It also bounds one request to at most 1,000 names, which is the bound [`internal/deletion`](../DESIGN.md) already applies to the same verb so that one request stays small enough to fail cheaply. Where a cluster advertises a smaller `max_deletes_per_request`, that smaller number applies. A reply that does not validate is not read as a disposition for any name in it: those names are recorded as effects this route could not learn, not as removals.
   - It is **reportable and optional**. Every outcome is one audit event per replaced name: what was removed, what was refused with the store's own reason, what the store's reply could not settle, and what a bounded inventory left behind. The audit vocabulary has no `partial`, so an incomplete removal takes the coarse `verify_mismatch` value that [ADR 0025](0025-local-interruption-outcomes.md) and [ADR 0027](0027-copy-interruption-outcomes.md) already use for partial outcomes, an unreadable reply takes `unverified`, and a reclamation that removed nothing because a rule declined it takes `observed`, because nothing was written. Only a removal that took everything it named is `applied`. The option defaults to reclaiming. It is read again where it authorises the deletion rather than carried from the question, and a settings store that cannot be read **there** declines instead of taking the default: the operator answered a sentence computed from a reading that worked, and removing objects after being told they would be kept is what that sentence exists to prevent. It may be an ordinary stored setting, and a page that can write settings cannot use it to cause a deletion, because the only direction that setting can move without a native confirmation is towards reclaiming **less**; the operation it qualifies is already gated by decision 2's confirmation, which no page can answer.

   **The answer bounds the KIND of effect, not its size.** What the operator authorises is whether this job may remove the predecessor's own recorded segments at all; the number the question states is what was there when they were asked, and the identities removed come from the record taken immediately before each publication. A predecessor that changed in between can therefore have a different number of segments, and the operation is still bounded to that object's own recorded whole entries. What may never happen is the reverse of the answer: a question stating the segments would be kept, followed by their removal, which is what the second reading of this decision failed at. So the permission is carried from the answered question into the run, where a later reading may restrict it — the option moved, the container now keeps versions, the record is missing, was never inventoried, or names nothing this operation may remove — and nothing can widen it.

   **The confirmation must say what will happen to the fragments.** An answer of yes has to cover the whole effect, so where reclamation is on and the live object is a large object, the question states how many segment objects will be removed after the replacement is verified, and where it is off or skipped it says they will be kept. A confirmation that describes only the name being replaced does not authorise deleting objects the operator was never shown, which is the one thing both earlier drafts of this decision agreed on.

   **The inventory is still a list of what the manifest names, not a complete graph of what backs the object**, and reclamation does not make it one. A static manifest's entries are exact; an inline entry has no remote object, a ranged entry references a containing object rather than a private one, and a nested static manifest names another manifest rather than its descendants. Reclamation therefore removes whole remote parts and **never** a ranged entry's containing object or a nested manifest's descendants: a shape that names something other than a private whole object is recorded, reported and left alone. A dynamic manifest's members are listed, so on an eventually consistent store the list may be short, and what was not listed is not reclaimed and is reported as not reclaimed.

   **What is not established, and stays not established.** Nothing here proves that no other object references a reclaimed segment. The live exclusivity binding [DESIGN §65.10](../DESIGN.md) owes would establish that, and until it exists this decision rests on the operator's accepted exposure and the reference implementation's precedent, not on proof. [ADR 0020](0020-recovery-containment.md)'s refusal to reclaim on inference is unchanged for every route that has not had this decision made about it.

6. **The replacement is still bound to its content.** The acknowledged publication drops `If-None-Match: *` and keeps the declared `ETag` of [ADR 0080](0080-upload-content-binding.md) wherever that route declares one, so a corrupted overwrite is answered 422 with the prior object intact, as measured. On a staged large object the manifest PUT carries an empty body, so an entity tag declared there would constrain that empty body and not the segments it names; none is declared, and the binding is the staged content comparison ADR 0080 decision 3 makes.
7. **What was observed is recorded as what was observed.** Before the publication the commit reads the live object and records its entity tag, length and last-modified as the **observed predecessor**. In the race this record admits, the object replaced may not be that one, so the ledger names what was seen rather than claiming to name what was replaced.
8. **The confirmation describes the container's observed versioning mode without promising recovery.** It says which mode the backend observed and which archive container it named, and it does not state that a previous version will be recoverable: the mode observed before a write is not bound through the write, which [ADR 0054](0054-versioning-preflight-authority.md) already keeps open, and no archive entry's bytes have been read by anything in this project. A container whose mode is unknown or unsupported is refused for overwrite, as ADR 0054 refuses editing it.
9. **Nothing else changes.** A name with no collision is published exactly as today. An unacknowledged job is published exactly as today. Mirror stays refused under ADR 0020 independently of this decision and of the capability gate.

## What the measurements settled, and what they could not

The operator offered two readings with their requirement and both proved load-bearing, so they are recorded with what measurement did to them.

- That the engine has a native way to handle this: true of the engine's own replacements, and this route now copies it. On a dynamic manifest it lists the predecessor's prefix, publishes, reads the container's versioning headers, then bulk-deletes the old segments in one account-level request, and with `X-History-Location` set it skips that delete entirely. Neither upload route lets the engine replace the live object, so its cleanup never runs for an aeronautes upload and the route performs the equivalent itself under decision 5. An earlier version of this record called that measurement irrelevant to this route; it was the strongest evidence in the record about what standard practice is, and dismissing it was the error decision 5's second draft rested on.
- That `?multipart-manifest=delete` might be the instrument, and that the engine might not use it: right on both counts, and the reason is worse than not using it. On a dynamic manifest it removes nothing, leaves the object readable, and buries `Not an SLO manifest` inside a 200 response body. A read-back confirms the object still assembles its full content afterwards.

What no measurement here could settle is the one thing reclamation would need to be PROVEN safe: whether anything outside this application references the predecessor's segments. That is a property of the whole account at a moment in time, not of a request, and DESIGN section 65.10 is where a live exclusivity binding is still owed. Until it exists, reclamation rests on the operator's accepted exposure and on the reference implementation's precedent rather than on proof, and the record says so wherever it says reclaim. **The operator's requirement is now met the way they asked: an overwritten large object's predecessor fragments are reclaimed once the replacement is verified, under an option that defaults to reclaiming, and the residue that reclamation cannot account for is reported rather than assumed away.**

## The risk this proposes to accept

Between the preflight that showed the operator a collision and the PUT that replaces it, another client can write that name, and this route will replace that write without noticing. The store offers no precondition that would catch it. Separately, a publication whose response is lost leaves what is at that name unknown until it is read again.

Neither exposure is reduced by any measurement in this record, and neither was carried by the operator's question of 25 September, which asked for overwrite support and ended by asking what it was missing. This record was the answer to that question, and the operator accepted these exposures on 26 September in the words the status records. The description is kept because the exposures are unchanged; the acceptance is no longer owed.

## Required proof before implementation is accepted

Tier 1 under [DESIGN §65.12](../DESIGN.md), on the mock and the owned Swift, through the public service.

- An unacknowledged upload onto a live name refuses as it does today, at preflight and at commit, with the prior object unchanged.
- An acknowledged upload with no confirmation raised, a confirmation answered no, and a confirmation whose raising fails, each refuse with the prior object unchanged and nothing recorded as applied.
- An acknowledged and confirmed upload replaces, records the observed predecessor's entity tag, length and last-modified, and reports the new object verified.
- Two accounts holding a same-named container with the same number of collisions: the confirmation names the account and bookmark the backend resolved, and an answer given for one does not authorise the other.
- The connection, generation or collision set changes between the confirmation and the start: the start refuses rather than proceeding on the earlier answer.
- On a container carrying a legacy versioning mode, the confirmation names that mode and its archive container, and an archive entry exists afterwards; on a container whose mode is unknown or unsupported, the overwrite is refused.
- An acknowledged upload replacing a dynamic large object: the replacement is readable afterwards, and the item's record names the set the predecessor held, whether that set was then reclaimed or kept.
- The same replacing a static large object: the inventory recorded is the exact list the manifest named, and the record says which of its entries are inline, ranged or nested rather than reporting them as remote parts.
- Reclamation on: an acknowledged replacement of a dynamic large object and of a static one each leave the new object verified and **every segment the predecessor's record named gone**, by one bulk delete per container whose per-object results are recorded, and the mutation trail carries one event for that name saying what was reclaimed. The report is the trail, not a job counter: decision 5's reportable rule is one audit event per replaced name, and a counter would claim a total where the per-name outcomes are what can be checked against the store. A set larger than one request's bound takes more than one request and every name in it is still accounted for; a cluster that advertises a smaller bound is believed.
- Reclamation off: the same two replacements leave every one of those segments in place, and the record says they were kept.
- The order: a replacement that publishes but fails verification reclaims **nothing**, and the predecessor's segments are all still there. This is the deliberate deviation from the engine and the case that proves it.
- Versioning: on a container that keeps versions, reclamation is skipped whatever the option says, the segments are all still there, the record says why, and an archive entry exists.
- The option read at the deletion: where the question was computed from a readable setting and the reading at reclamation time fails, nothing is removed and the record says the setting could not be read.
- The answer as a ceiling: a question stating the segments would be KEPT, followed by the option moving before the job runs, removes nothing and the record quotes the sentence it kept. A question that could not read what backs the object says so rather than saying there is no large object, and authorises nothing.
- The report: a store's refusal and a name in a reply that could not be read are recorded apart, an inventory whose every entry is an excluded shape removes nothing and is not recorded as applied, and one identity named twice by one manifest is one deletion and one result.
- The shapes: a static manifest holding a ranged entry and a nested manifest entry reclaims neither the ranged entry's containing object nor the nested manifest's descendants, reports both as left alone, and reclaims the whole remote parts beside them.
- The limits: an inventory that could not be read reclaims nothing; one truncated at this build's bound reclaims only the entries it holds and reports the remainder as left behind; a dynamic manifest whose listing was short reclaims only what was listed.
- The confirmation states the number of segment objects that will be removed when reclamation is on and that they will be kept when it is off, and an answer of no removes nothing. The option is reachable where the operator sets the application's other bounds, and that control shows the last observed setting until a save is acknowledged.
- The exposure, stated as a case rather than hidden: an outside manifest built over the predecessor's prefix loses its backing data when reclamation removes those segments, and the test records that this is the accepted consequence rather than a defect. With reclamation off, the same outside manifest still assembles its own bytes.
- Publication refused: where the replacement was not attempted, or is proven refused, the predecessor's manifest and every one of its segments are unchanged.
- Publication landed or unknown, then a later step fails: the record reports the live outcome as observed or as unknown and claims no rollback, the predecessor's fragments are all still there because reclamation follows a verification that did not happen, and nothing asserts that the old manifest survived. A lost response to the replacement is one such case and a verification read that fails after a successful write is another.
- The control: replacing a plain object with a plain object records no segment inventory and touches no segment container at all.
- An acknowledged upload whose body is altered in flight is refused by the store, and the prior object is unchanged.
- A name with no collision in an acknowledged job still publishes conditionally: a racing create of that name between preflight and commit is refused as a conflict, not replaced.

Retained mutants: the acknowledgement checked without the native confirmation; the confirmation raised after the conditional is dropped rather than before; the confirmation naming only the container and the count, which must fail the two-account case; the answer reused for a changed plan; the predecessor's inventory read after the replacement rather than before it, which can recover nothing; an inline, ranged or nested static entry reported as a remote part; a landed or unknown publication reported as a refused one, which must fail the case that forbids a rollback claim; the conditional dropped for every name in an acknowledged job rather than for the acknowledged collisions; the observed predecessor recorded after the replacement rather than before.

Reclamation's own mutants: refusing for want of somewhere to record the outcome AFTER the deletion rather than before it, which makes the refusal's own sentence false; crediting a bulk-delete reply that did not validate; sending one unbounded request for a set larger than the bound; reclaiming before the verification rather than after it; reclaiming on a container that keeps versions; reclaiming a ranged entry's containing object or a nested manifest's descendants; reclaiming a prefix listed at the time of deletion rather than the identities recorded before the publication; reclaiming the whole named set when the inventory was truncated or unread; ignoring a bulk delete's per-object results and reporting a partial success as a complete one; the option ignored, in either direction; and the confirmation left silent about the fragments while reclamation is on, which must fail the case that requires the question to state what will be removed.

The native journey that shows what the confirmation actually renders remains the operator's, as the [0.1.0 test plan](../audits/2026-09-24/0.1.0-test-plan.md) records for ADR 0073's dialogs.

## What this does not establish

It does not close finish-line item L05, lift the capability gate, or lift the valuable-data release hold. It does not change Copy, Mirror or deletion, and the only objects it removes are the ones decision 5 names: a replaced large object's own recorded segments. It does not lift [ADR 0020](0020-recovery-containment.md)'s refusal of reclamation on inference for any other route. Decision 5 is a single, named exception to it, made by the operator on a stated exposure and on the reference implementation's precedent, and it is not a general licence: no other route gains authority to reclaim anything, and the live exclusivity binding that would turn this exception into proof is still owed by DESIGN section 65.10. It does remove objects — the predecessor's own segments, after a verified replacement, unless the container keeps versions or the option is off — which every earlier draft of this record said it would not. It does not establish behaviour on a modern-versioned container, whose editing ADR 0054 still refuses, and it makes no claim about a deployed cluster.
