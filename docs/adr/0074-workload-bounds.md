# ADR 0074: bounds for browser retention, queued work, child batches and aggregate resources

**Status:** Accepted on 24 September 2026 with the proposed values as defaults (the operator's words: "yes make them sane defaults with option to override, unless that creates a test nightmare"); all three slices implemented on 24 September 2026, and the delivered values accepted as the v1 bounds later that day (the operator's word: "accepted"; finish line decision 15), which closes L10.
Its context names one active job; [ADR 0105](0105-concurrent-jobs.md) raised that to two by default and four at most, with the queue depth of decision 2 unchanged and the aggregate worker and memory ceilings still unbuilt.
Slice 1 delivered decisions 1 and 2. `browserRetentionCeiling` (default 100,000, range 1,000 to 5,000,000) and `maxQueuedJobs` (default 16, range 1 to 1,000) are application settings with the download ceiling's treatment: a zero keeps the default, a value outside the range is refused rather than clamped, and the jobs drawer carries both. A column at the ceiling keeps every row it holds and shows the notice in place of the next page; a column that reaches the default before the settings were shown reads them, so the stop is the operator's ceiling. The runner refuses a start once as many jobs wait for a slot as the depth allows ("the job queue is full: 16 jobs are waiting; wait for one to finish or cancel one"), before any job row or credential pin exists, and a cancelled queued job frees its place. A page reply carries `effectiveLimit`, the size the bridge applied; the browser keeps it in its mirror and has no logic that depends on the size it asked for. The tests are `TestSettingsServicePersistsAndApplies`, `TestQueueDepthRefusesAtTheBoundary` and `TestPageReplyCarriesTheEffectiveLimit` in `internal/app`, and the retention ceiling cases in `frontend/src/features/browser/pagingBinding.test.ts`.
Slice 3 delivered decisions 4 and 5. `maxConnsPerHost` (default 16, range 1 to 256) is an application setting with the same treatment; a native session opens with it and caps the connections it holds to one host, every trust mode included, so a burst of inspector reads and Find scans waits for a connection rather than opening one without bound; a changed cap applies to sessions opened afterwards. Find's match truncation stays as it was. The tests are `TestSessionTransportCarriesTheConnectionCap` and `TestSessionCapsConnectionsPerHost` in `internal/swiftcontrol`, and `TestSessionsOpenWithTheOperatorConnectionCap` and `TestControlPlaneAnswersUnderLoad` in `internal/app`, the latter holding a download child and four parked Find scans while a listing page and a settings read answer within five seconds against the mock.
Slice 2 delivered decision 3. The download route gives its engine-routed names to the child in batches of 500 names or 64 GiB of planned bytes, the copy executor's values shared as `DefaultBatchNames` and `DefaultBatchBytes`, in plan order; the stage directory is one per job as before, admission of every item still precedes the first child, and each batch is copied, checked for a displaced stage and placed before the next child starts. A child that fails or a stage that was displaced ends the run with that batch recorded as before and every later batch's items recorded as not attempted; a cancel between batches records the current batch's unplaced items as a cancel inside placement does and the later batches as not attempted. The batch bounds are constants rather than settings: they follow the copy route, and the ADR 0072 ceiling already bounds a selection. `--buffer-size` is emitted for every job, 16Mi unless the job's settings override it within 1Mi to 1Gi, on every profile and on the local routes, and the recorded effective settings carry it. The tests are the batch cases in `internal/transfer/local/download_batches_test.go` (three children for 1,001 names, a failed second child, a cancel between batches, a displaced stage, the byte bound), the argv case in `internal/transfer/rclone`, the buffer size cases in `internal/app`, and the real-child boundary case in `internal/systemtest`.
**Scope:** The areas finish-line item L10 still names for the capabilities v1 keeps: browse, inspect, download, metadata editing and creation. The download inventory ceiling is delivered under [ADR 0072](0072-large-namespace-handling.md) and is not changed here.
Amended on 16 November 2026 by [ADR 0122](0122-the-stores-answer-is-the-result.md) decision 5: a download's batch whose child fails no longer ends the run; each file of it has its outcome and the next batch goes to a child, as a copy's always have.

## What exists, at master `df96e1ad`

- Listing: the browser asks 1,000 rows a page (`frontend/src/features/browser/browserState.svelte.ts:50`); the bridge clamps any ask above 5,000 silently rather than refusing it (`internal/app/browseservice.go:106`); Swift's default page is 10,000 (`internal/swiftcontrol/containers.go:14`). Container and object rows accumulate with no cap until navigation resets them (`browserState.svelte.ts:616`, `:763`).
- Queued work: one active job under [ADR 0047](0047-single-active-job.md) (`internal/app/transferservice.go:93`); a job admitted over capacity parks in the runner with no bound on how many may wait (`internal/app/jobrunner.go:251-256`); a queued job cancels cleanly before it starts.
- Child batches: the download route hands one engine child the whole engine-routed name list of a job (`internal/transfer/local/download_execute.go`, `copyIntoStage`), bounded only by the ADR 0072 ceiling, while the copy executor batches 500 names or 64 GiB per child (`internal/transfer/copy/executor.go:150`); `--buffer-size` is never emitted (`internal/transfer/rclone/runner.go:415-428`), so the engine's own per-transfer default applies unmanaged; the gateway bounds child connections to a capacity between 64 and 1,024 (`internal/transfer/rclone/runner.go:398-399`, `gatewayCapacity`) and bulk bodies to 4 MiB (`internal/transfer/rclone/gateway_scope.go:13`).
- Aggregate: the native Swift client has no concurrency or rate bound of its own (`internal/swiftcontrol/tls.go:42` wraps the default transport); Find keeps 1,000 matches with an honest truncation flag, refuses a fifth concurrent scan and retains sixteen records (`internal/app/findservice.go:98-102`); audit history keeps 10,000 rows (`internal/audit/audit.go:79`) and the settings default to a 90-day audit window (`internal/app/settingsservice.go:98`); one session is cached per bookmark with no expiry (`internal/app/connections.go:34`).

## Decision, proposed

1. **Browser retention ceiling.** A column stops loading further pages once it holds N rows (proposed 100,000), keeps every row already shown, and says so in place of the next page: "100,000 rows loaded; narrow the prefix, use Find, or count the prefix". Nothing shown is dropped, so correctness is not truncated, and the ADR 0072 count gives the exact total. The bridge's silent clamp becomes visible: the page reply carries the effective limit, so the browser never believes it asked for more rows than it was given.
2. **Queue depth.** The runner refuses a new job when N jobs already wait behind the active slot (proposed 16): "the job queue is full: 16 jobs are waiting; wait for one to finish or cancel one". Cancelling a queued job keeps releasing its claim as today.
3. **Child batches on the download route.** The engine-routed names of a job go to the child in bounded batches (proposed 500 names or 64 GiB of planned bytes, the copy executor's values); each batch is staged, verified and published under the existing recorder semantics before the next child starts, so an interrupted job leaves at most one batch's stage behind. `--buffer-size` is emitted explicitly from the profile (proposed 16 MiB, the engine's default, so nothing changes until the operator changes it), and the effective settings show transfers × buffer as the child memory the operator can reason about.
4. **Aggregate resources.** The native client gets a per-host connection cap (proposed 16) so a burst of inspector reads and Find scans cannot open unbounded connections to one endpoint. Find's match truncation stays as it is: the scanned count is exact and the flag is shown, which this record proposes to accept rather than change.
5. **Control plane.** A maintained test shows that while a download runs and Find is at its worker limit, a listing page and a settings read still answer within a bound (proposed five seconds against the mock).

The values in parentheses are the author's proposals; each is the operator's decision.
Decision 7 of 23 September made the download ceiling a setting; the retention ceiling and the queue depth could take the same settings shape if the operator wants them configurable.

## Consequences

Items 1, 2, 4 and 5 are tier 2 under DESIGN §65.12; item 3 is tier 1, because staged effects and their records now span batches.
Three delivery slices would follow acceptance: retention and queue depth (browser and runner, with their tests), download batching (executor and recorder, proved on the mock and the owned Swift), and the client cap with the responsiveness test.

## Decision 6: the object list pages past the ceiling (18 November 2026)

Testing the 0.5.0 candidate with the ceiling at 1,000, the operator found the object list stops at the ceiling with nothing to press, and asked: "why don't we actually tell it to load more? that seems reasonable.. it's like paginated".

1. **The notice offers the next page.** When the object list holds as many rows as the ceiling and the store has more, the notice keeps its words and gains a button, "Next N →", N the ceiling.
   Pressing it replaces the rows shown with the rows that follow the last one, read from the same marker "Load more" would use, and "Load more" then fills that page up to the ceiling as before.
   The rows held never exceed the ceiling, which is what decision 1 bounds.
   "The store has more" means a row follows the page: a Swift listing does not say whether it is the last, so each page of objects or containers asks the store for one row more than it returns, and only that extra row's presence sets the page's next marker.
   A listing that ends exactly at a page's end, such as 2,000 objects read 1,000 at a time, therefore offers neither "Next N →" nor "Load more" after its last row, as the operator found on 18 November: "if there are no more, it shouldn't give the next button".
2. **Where you are.** Past the first page the footer counts the rows from the start of the listing ("rows 1,001 to 2,000 (more on server)"), and the notice and the footer both offer "← Back to the start", which reads the listing again from its first row, as moving into the folder does.
   There is no previous page: the store lists forward from a marker only, and going back one page would need every earlier marker kept, for a gain the start and Find already give.
3. **A page change ends the selection.** Moving to the next page or back to the start clears the selection and the inspector, as moving to another folder does, so a deletion, copy or download never acts on rows that are no longer shown.
   Find, the count and a folder's or container's own actions are unchanged: they act on the whole scope, not on the rows shown.
4. **What does not change.** The ceiling setting, its range and its default; the container column, which still stops at the ceiling with its notice; and the filter box, which filters the rows shown.

**Required proof (tier 2).** Frontend, on the browser state with a fake bridge: at the ceiling with more on the server the next page replaces the rows with the following ones from the held marker, the footer's numbers count from the start, the selection is cleared, and back to the start lists from the first row; under the ceiling nothing changes. Journey, on the mock with the ceiling at 1,000 and a prefix of 2,000 objects: the next page shows the 1,001st name first and back to the start shows the first, and that second page, which ends the listing, offers no further page.
Backend, on the mock store: an object page and a container page that end exactly at the listing's last row carry no next marker, and a page with a row after it does.

## What this does not establish

Per-endpoint budgets (DESIGN §38.2), adaptive concurrency (§38.4), the SQLite size cap and segment-evidence retention (§51) stay open beyond v1.
L10 completes for v1 only when the operator accepts these bounds and the slices land; nothing here changes a gate or the valuable-data release hold.
